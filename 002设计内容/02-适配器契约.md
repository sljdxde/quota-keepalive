# 02 · 适配器契约

> 状态：v1.4（2026-10-29）· 目标：满足 FR-2、FR-3、FR-4、FR-9、FR-12、FR-14、FR-15、FR-16、FR-20 与 NFR-2、NFR-4。适配器是"目标应用 agent"（FR-14）的唯一提供方：本体只把适配器声明的东西原样对外暴露，不添加目标应用专有逻辑。

## 定位与边界

适配器是一个目标应用的普通 npm 包：它负责该应用的账号发现、可选官方登录描述、签到/保活协议和结果解析；qka 本体负责统一的 MCP 能力、日界状态、日志、账号与来源状态、登录会话、凭据生命周期和网络出口。调度既不属于适配器，也不属于 qka；它只属于宿主。新目标应用的正常接入路径是新增适配器，而不是修改本体的目标应用业务代码。

“本体零改动”指不需要为 WorkBuddy CN、Qoder、Qoder CN、豆包工作等新增专用分支；如果某目标应用确实需要一个此前不存在的**通用**系统能力，必须先扩展并版本化能力契约，不能把例外伪装成零改动接入。

## 包与清单

```
qka-<target>/
├── package.json
├── manifest.json
├── index.mjs
└── …
```

```jsonc
{
  "id": "qoder-cn",
  "name": "Qoder CN",
  "version": "1.2.0",
  "entry": "./index.mjs",
  "capabilities": ["accounts.discover", "login.official", "checkin"],
  "needs": ["credentials.discover", "credentials.resolve", "credentials.managed", "login.open", "http.outbound", "state.daykey"],
  "actions": [
    {
      "op": "checkin",
      "effects": { "accessesNetwork": true, "mutatesTarget": true, "spendsCredits": false, "idempotent": true, "mayRequireReauth": true }
    },
    {
      "op": "keepalive",
      "costHint": { "unit": "credits", "approx": 0.02, "source": "latest_live_probe" },
      "effects": { "accessesNetwork": true, "mutatesTarget": true, "spendsCredits": true, "idempotent": true, "mayRequireReauth": true }
    }
  ],
  "dayRule": { "tz": "Asia/Shanghai" },
  "compatibility": { "qka": ">=1.0.0" }
}
```

- WorkBuddy CN 同时声明 `keepalive`；没有该能力的目标应用不会收到保活调用（V1 只有它声明）。
- `actions[].effects` 是 FR-15 效应声明的**唯一来源**：本体原样投影到 MCP，不自行猜测。声明缺失的效应位一律按最保守值（true/非幂等）对外暴露，并计入 `doctor_run` 的适配器质量告警。
- `costHint` 供面板与 `plan_validate` 预估当日成本，满足需求文档 §7 第 2 条（保活净消耗必须可见）。
- manifest 不声明默认时刻表、时区计划、宿主注册状态或任何调度字段。`dayRule.tz` 只定义每日幂等的业务日界，不触发执行。
- `id` 在市场中全局唯一；能力、所需钩子、日界和兼容版本都是签名内容。
- 新增 `actions` 与 `effects` 字段后，签名覆盖范围随之扩大：效应声明被篡改即验签失败（防"声明只读、实际写入"）。
- 一个版本的签名必须绑定规范化制品清单（每个文件的路径与哈希）或完整归档哈希，不能只签 `manifest.json`。

## agent 自描述视图（FR-14）

本体把每个已加载适配器封装成一个**目标应用 agent**，经 `agents_list` 与 `qka://agents` 对外暴露：

```jsonc
{
  "id": "qoder-cn",
  "name": "Qoder CN",
  "adapterVersion": "1.2.0",
  "operations": ["checkin"],
  "capabilities": ["accounts.discover", "login.official", "checkin"],
  "needs": ["credentials.discover", "credentials.resolve", "credentials.managed", "login.open", "http.outbound", "state.daykey"],
  "effects": { "checkin": { "mutatesTarget": true, "spendsCredits": false, "idempotent": true } },
  "enabled": true,
  "available": true,
  "unavailableReason": null,
  "scheduleOwner": "host",
  "lastInvocationAt": "2026-10-29T10:10:31+08:00",
  "accounts": [{
    "id": "u_123",
    "label": "qoder@…",
    "state": "ready",
    "preferredSource": "src_managed_1",
    "sources": [
      { "id": "src_managed_1", "kind": "managed", "state": "ready", "lastVerifiedAt": "2026-10-29T10:09:55+08:00" },
      { "id": "src_imported_1", "kind": "imported", "state": "ready", "lastVerifiedAt": "2026-10-29T09:00:00+08:00" }
    ]
  }]
}
```

- 该视图**完全由 manifest + 本体状态拼装**：本体代码里没有任何 `if id == "qoder-cn"` 分支，这是 NFR-4 的硬约束。
- 适配器热更新后视图自动刷新；`available` 与 `unavailableReason` 区分"未登录""需重登""平台不支持""适配器已停用""签名校验失败"。
- `scheduleOwner: "host"` 是固定职责说明，不是注册状态；`lastInvocationAt` 只是 qka 收到一次调用的时间，不证明宿主已创建未来计划。
- 一个账号可有一到多个登录态来源。`kind=managed` 允许仅按官方机制刷新；`kind=imported` 永远只读，不刷新、不回写。
- 宿主据此决定能做什么，而不需要为每个目标应用写专用提示词——这就是"多 agent"的落地形态（不吸收动态工具名的理由见需求文档 §6.1）。

## 运行时协议

### 本体调用适配器

- `accounts.discover`：返回已登录账号及可用来源，每项含稳定账号 id、展示名、来源 id、来源类型、健康状态和脱敏元数据；不返回 token。发现失败应区分“未登录”“需要重新登录”“当前平台不支持”。
- `login.begin`（可选，仅 `login.official`）：返回一个可见的官方登录启动描述（例如目标应用 deep link 或厂商登录 URL）。qka 在独立窗口/目标应用内展示它，不注入输入框、不读取键盘/扫码内容；关闭窗口不等于成功。
- `login.verify`（可选）：官方登录返回后，以只读身份接口或一次无副作用查询验证会话。只有验证出目标账号后，qka 才保存受管来源并标记完成。
- `checkin.run`：对一个账号执行一次领取或复核，返回标准结果。
- `keepalive.run`：仅对声明了该能力的账号执行一次最低成本真实使用，返回标准结果。
- `health.ping`：供升级、恢复和诊断使用，不产生目标应用侧动作。
- 本体在派发前用 manifest 校验：未在 `actions` 中声明的操作不会下发；`effects.mutatesTarget === false` 的操作被本体拒绝走写路径。
- 适配器不能声明时刻表、注册宿主计划或要求 qka 定时回调；每次 `checkin.run` / `keepalive.run` 都由外部 MCP 调用触发。

### 适配器调用本体

- `credentials.discover` / `credentials.resolve`：按适配器、账号与显式 source id 返回只在当前调用有效的凭据引用及脱敏元数据；明文仅在必要的内存调用链中存在，不能进入状态、日志或 MCP 返回。导入来源只提供只读引用；受管来源才可按官方机制刷新。
- `login.open`：只允许打开适配器声明的官方登录入口；qka 负责可见窗口、超时、状态回传和只读完成校验。适配器不得获得用户键入内容。
- `credentials.managed`：受管来源的加密持久化由 qka 的 Keychain 能力完成；适配器只能请求刷新或读取当前调用引用，不能自行落盘 token。
- `http.fetch`：由本体统一处理出站、UA、超时、日志脱敏和允许的目标范围。
- `state.get/set`、`log.write`：只能读写自身账号和当前操作命名空间的状态与日志。

### 来源选择与失败隔离

- 账号与登录态来源分离；删除来源引用不会删除目标应用账号或数据。
- 同一账号多个来源时，默认顺序为用户显式固定 > 健康受管来源 > 健康导入来源；qka 记录本次实际来源。
- 某来源失败只影响该来源及其所属账号，不自动覆盖其他来源或账号。导入来源失败即停止使用该引用；受管来源仅在官方刷新路径内恢复。
- qka 不因一个来源失败而写目标应用文件，也不把导入来源转成受管来源。

### 标准结果

```jsonc
{
  "state": "signed | completed | already | none | failed",
  "credits": 100,
  "balance": 2050,
  "message": "今日签到 +100 Credits",
  "retryable": false
}
```

`signed` 和 `already` 表示签到领取动作不应重复；`completed` 表示保活已完成；`none` 表示活动尚未放量，必须保留后续触发机会；`failed` 交给 qka 的退避策略。是否需要午后复核由 qka 的每日操作状态决定，而不是让适配器重复领取。

## 签名、来源与热更新

- 市场索引给出 id、版本、下载地址、制品哈希、签名和兼容范围；本体仅加载使用内置可信公钥验证通过的制品。
- 默认来源是官方索引。用户添加第三方来源时，必须同时显式信任其公钥；第三方适配器是用户主动信任的代码，不等同于 qka 官方审核。
- 更新时机是启动、每 6 小时和手动刷新。适配器管理器将正在执行的版本固定到任务结束，再验证、加载新版本；加载或健康检查失败时保留上一版本。
- 无可回退版本时禁用该适配器并在面板告警，绝不以未知版本继续访问凭据。

## 隔离与权限语义

- Bun 子进程首先提供崩溃与生命周期隔离；本体对 IPC 钩子严格按 `needs` 授权，越权调用直接拒绝。
- 适配器必须经本体钩子使用凭据、状态、日志和标准 HTTP 出口；凭据不可持久化，日志由本体二次脱敏。
- 本期的“子进程隔离”不是对同一 macOS 用户下恶意本地代码的完整安全沙箱。官方签名、来源白名单和最小 IPC 能力共同定义可接受的信任边界；若以后承诺抵御恶意适配器，需另行设计 OS 级沙箱。

## 目标应用参照（V1 / V2）

| 版本 | 适配器 | 能力 | 参照 |
|---|---|---|---|
| V1 | WorkBuddy CN | 账号发现、签到、保活 | `dsh-buddy-checkin`、`dsh-workbuddy-keepalive`（真实对话探针，最近一次实测 0.02 积分）、`dsh-connect-workbuddy` |
| V1 | Qoder CN | 账号发现、签到 | `dsh-qoder-checkin`；每日活动 id 现读现用 |
| V1 | Qoder | 账号发现、签到 | 与 Qoder CN 是两个独立 App、额度独立；活动与凭据差异待真机确认 |
| V1 | 豆包工作 | 账号发现、官方登录、签到 | 独立产品（非豆包电脑版）；个人账号真实签到和到账已通过，凭据、UA、接口限制与 `idempotent: false` 以[目标应用真机实测](<../.scratch/wayfinder/research/target-apps-live-test.md>)为准 |
| V2 | Trae / Trae CN | 账号发现、签到 | magpie `internal/provider/trae_checkin.go`；真机实测 |
| V2 | 千问办公 | 账号发现、签到 | 无现成参考，需先调研产品形态与凭据位置 |

适配器对目标应用的凭据位置、请求字段和风控差异负责；这些实现细节不得泄露到统一 MCP 工具面。

WorkBuddy CN 保活的具体契约（对齐 dsh 实现）：`keepalive.run` 必须发出**真实的对话请求**（dsh 为 25k 输入 + 1 输出 token），拿到真实模型回复才算成功；不接受伪造心跳或仅建立连接。成本按当次上游结算回执展示，最近一次真机实测为 0.02 积分，不再把 0.72 写成固定值。单日最多成功一次；失败有 10 分钟冷却门槛，但后续真实重试仍由宿主或手动调用触发。

## 用户自研插件（FR-21）

- 仓库提供 `adapters/_template/` 模板与 `qka adapter init` 脚手架，生成可直接运行的 npm 包骨架（package.json、manifest.json、index.mjs、测试桩）。
- `qka adapter validate <dir>` 离线校验：manifest schema、`capabilities`/`needs`/`actions`/`effects` 完备性、入口文件存在、兼容版本范围，不需要联网也不需要凭据。
- 本地开发包默认**不可加载**；用户显式打开"开发者模式"后才可加载未签名包，并在 `agents_list` 与面板中标注 `unverified: true`，不进入自动更新通道。
- **凭据边界（用户 2026-10-28 拍板的折中方案）**：未签名适配器不得继承该目标应用的全部凭据；只能读取用户**当场为它指定的单个账号、单个已有登录态来源**。授权仅当次调用有效，不写缓存、不写状态文件；每次加载都要弹确认，显示包名、来源类型/路径、请求的目标应用与账号，并写审计日志。未签名适配器不能创建受管来源，也不能因失败触发官方刷新。
- 发布仍走 FR-9：签名、市场索引、回退。第三方适配器是用户主动信任的代码，不等同官方审核；开发者模式不是绕过签名的通道，只是"单账号、一次性"的受限测试口。
