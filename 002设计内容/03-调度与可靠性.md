# 03 · 宿主调度与执行可靠性

> 状态：v1.4（2026-10-29）· 落实 FR-3、FR-4、FR-5、FR-8、FR-12、FR-15 与 NFR-3、NFR-6、NFR-7。

## 职责边界与触发

**宿主是唯一调度器；QKA 是单次执行器。**

- 宿主在自身产品中按用户自然语言意图创建、保存、修改和删除定时任务；到点通过 MCP 调用 `checkin_run`。
- QKA 不提供 `schedule_get`、`schedule_set` 或等价工具，不保存期望时刻表，不读取宿主内部计划，也没有本地兜底定时器。
- 面板“立即执行”和宿主计划调用进入同一条执行链，区别只在调用方；二者都受北京日界幂等、租约和冷却约束。
- 每个支持的宿主在安装档案中说明如何**在宿主自身界面创建和核验**原生计划；QKA 只提供指引和最近调用时间，不能证明未来计划一定存在。
- 没有宿主调用时，QKA 不执行签到或保活，也不会在睡眠唤醒后自行补跑。恢复后的首次宿主/手动调用会按当前状态决定是否还有工作。

## 推荐宿主计划

- 日界固定为 `Asia/Shanghai`；推荐宿主创建**每小时一次**的原生计划（示例 `00:10、01:10 … 23:10`），但具体起止时间与频率由用户在宿主中设置。
- **当日成功即停**：某账号当天签到到达 `signed_provisional` / `signed_confirmed` / `already` 后，后续巡检对它只做状态汇总、不再发外部领取请求；保活与午后只读复核不受此限制。
- 每次调用会展开为目标应用下的启用账号和适配器声明的操作；账号是否执行由账号状态决定，不由 QKA 的时钟决定。
- 最近调用超过用户可配置的提醒阈值时，QKA 在面板显示“宿主近期未调用”，并给出宿主计划核验步骤；它不自动创建计划，也不能断言宿主计划已失效。
- WorkBuddy CN 的保活与签到独立：一次调用中若签到与保活都需要执行，可以同轮完成；签到成功不使保活跳过。V1 只有 WorkBuddy CN 收到 `keepalive.run`。
- 保活成功判据对齐 dsh `dsh-workbuddy-keepalive`：必须拿到真实模型回复（25k 输入 + 1 输出 token），**单日最多成功一次**。成本按当次回执展示，最近一次实测为 0.02 积分。
- 保活失败后进入 10 分钟冷却，不消耗当天次数；10 分钟后只有新的宿主/手动调用才会重试。宿主默认每小时调用时，下一次机会通常是下一个小时，QKA 不会自行在 10 分钟后唤醒。

## 每日操作状态机

状态键为：`目标应用 × 账号 × 操作（checkin/keepalive）× 北京日期`。

```
签到：pending → running(lease) → signed_provisional → signed_confirmed
                         ├→ already
                         ├→ none → pending（等待下一次宿主/手动调用）
                         ├→ failed_retryable → pending（等待下一次宿主/手动调用）
                         └→ failed_final

保活：pending → running(lease) → completed
                         ├→ failed_retryable → pending（退避结束后）
                         └→ failed_final
```

- `signed_provisional` 表示已经领取且不能再次领取，但午后仍需走只读复核；它不是可以再次签到的状态。
- 12:00 前成功的签到进入 `signed_provisional`；午后复核成功才进入 `signed_confirmed`。12:00 后首次成功可直接确认。
- `already` 是当天领取动作的终态；`completed` 是当天保活动作的终态；`none` 不是终态；凭据失效、用户明确停用或适配器声明不可恢复时才进入 `failed_final`。
- 同一键由 SQLite 唯一约束和条件更新取得执行租约。租约持有者崩溃或超时后可恢复为待执行；多个宿主调用或用户手动点击同时到达时，也只能有一个外部请求。

## 重试、恢复与告警

- 签到类可重试失败**不由 QKA 定时重试**，直接等下一次宿主或手动调用；调用之间返回当前状态而不访问上游。保活失败同样进入 10 分钟冷却门槛，真实重试由后续调用触发。
- **告警呈现**：签到失败在菜单栏显示红点，进入面板可看到目标应用、账号、失败原因、已尝试次数与下一步；默认不弹系统通知，系统通知仅在"需要重新登录"等需用户动作时作为可选项触发。
- 凭据失效：红色告警并停止该账号当日后续自动重试，提示用户回目标应用重新登录；下次账号发现成功后自动恢复。
- 网络和上游错误：静默等待下一次宿主调用；协议变化或适配器不可加载：红色告警，提示更新或停用适配器。
- 状态快照以 0600 权限 tmp+rename 原子写入，用于故障恢复；SQLite 是账号来源、每日操作状态、租约和日志的唯一真源，不保存宿主计划。

## 日志、到账与返回

- SQLite 日志一行一事件，记录触发、租约、外部结果、复核、更新和错误；滚动保留最近 48 小时。
- 面板可按目标应用、账号和操作筛选。成功显示到账与余额；待确认、待重登和退避状态可区分。
- MCP 对每个账号 × 操作返回统一结构，成功和失败都必须带 `state`、时间、可读说明；可取得时带 `credits` 与 `balance`。

```jsonc
{
  "target": "qoder-cn",
  "account": "u_123",
  "operation": "checkin",
  "state": "signed_confirmed",
  "credits": 100,
  "balance": 2050,
  "at": "2026-10-28T10:10:31+08:00",
  "message": "今日签到 +100 Credits",
  "evidence": {
    "observed": [
      { "kind": "request", "endpoint": "openapi.qoder.sh/me/campaigns/claim", "status": 200, "at": "2026-10-28T10:10:30+08:00" },
      { "kind": "balance_delta", "before": 1950, "after": 2050 }
    ],
    "inferred": [
      { "claim": "本次 +100 来自每日活动", "confidence": "high", "basis": "活动 id 与余额差值一致" }
    ],
    "unknown": [
      { "item": "上游是否另有未展示的到账", "reason": "无可只读校验的来源" }
    ]
  }
}
```

## 到账证据纪律（FR-8）

- **观察 (observed)**：工具返回里可直接核查的事实——请求端点（脱敏）、HTTP 状态、时间戳、前后余额。这是唯一可以支撑"已到账"断言的证据类型。
- **推断 (inferred)**：由观察得出的解释，必须带置信度与依据。宿主在对话中转述时要保留"推断"标签。
- **未知 (unknown)**：本次执行覆盖不到、或证据冲突的点，必须显式列出。
- **硬规则**：`signed_confirmed` 只在观察到余额增加或上游明确回执时才可返回；仅有领取动作成功而无余额证据时，状态停在 `signed_provisional`，文案为"已领取，待复核"。缺证据绝不转成"没发生"，也不许转成"已到账"——两个方向都不允许。
- 证据里不出现凭据、完整请求头、cookie 或原始响应体；端点按白名单脱敏。

## 预演与效应（FR-15、FR-17）

- `plan_validate` 基于**当前时刻、启用账号与适配器 `actions`/`effects`** 计算：若现在调用将发起的外部请求数、可能消耗的额度（用 `costHint` 估算）、冲突（同日已终态、冷却中、来源失效）与将产生的状态迁移，全程不发外部请求、不写状态。
- 面板"立即全部执行"与宿主调用前都可先取该预演结果，作为 §7 第 2 条（保活净消耗可见）的落点。
- 每个返回给宿主的结果附带本次动作的效应摘要，宿主可据此判断是否需要先征询用户。

## 唤醒与节流（NFR-7）

- QKA 不创建业务定时任务；仅更新检查、适配器拉取和冷却状态维护等维护循环采用**对齐唤醒**。
- 系统睡眠期间宿主计划是否补跑由宿主决定；QKA 被唤醒调用时重新读取当前日期和来源状态，不因错过某个整点自行补执行。

这套模型满足已确认的职责边界：**宿主独占“何时调用”，QKA 独占“这次能否执行”**。不存在 QKA 计划、本地兜底或双通道竞争。
