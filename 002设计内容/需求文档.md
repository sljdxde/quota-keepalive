# QKA 需求文档

> 版本：v1.4（2026-10-29）· 读者：后续接手的 agent 与人
> v1.0 是需求基线；v1.1 吸收 **rea** 的 MCP 工具契约（效应声明、证据纪律、doctor/dry-run）与 **magpie** 的常驻工程优点，把功能需求从 13 条扩到 19 条；v1.2 按用户确认的**版本节奏**重定目标应用范围（V1 四个 / V2 三个），并补上手动配置与插件开发两条需求；v1.3 按用户拍板改写巡检节奏、失败呈现与插件开发者模式的凭据边界；v1.4 统一登录态来源与调度职责：QKA 不收集账密、验证码或扫码内容，但可启动目标应用官方登录；宿主独占调度权，QKA 不创建、保存、修改或补充定时任务。共 **21 条功能需求 + 8 条非功能需求**，编号只追加不复用。
> 本文回答「**为什么做、要什么**」；技术方案见 [00-06 设计文档](00-产品定义与UI.md)；决策过程与依据见 [.scratch/wayfinder/map.md](../.scratch/wayfinder/map.md)（wayfinder 地图，含全部研究工单结论）。

## 1 · 背景与初始需求（2026-10-28，用户原始表述整理）

国内的 AI 工具——WorkBuddy、Qoder、Trae、豆包工作等——普遍有「签到领额度」「账号保活」类活动，但领取要每天手动操作，忘一天就损失一天额度。

当时已有的方案是 dsh（DeepSeek Harness）里的签到插件（workbuddy、qoder 等），**缺点是只能在 dsh 里用，对普通人门槛过高**。由此提出初始需求：

1. 做一个 agent 工具，用户可以在**任意 harness 工具**里配置和安装；
2. 有个**菜单栏**，让用户登录/管理自己的 AI 工具账号；
3. 自动**签到**和**发消息保活**；
4. 签到活动经常变化 → 工具要支持**频繁更新**；
5. 整体界面与框架参照 **magpie** 的思路；
6. 设计内容统一放项目的**设计文件夹**；
7. 同时承载**签到活动检索、优惠活动检索**（后划出本期，见 §5）；
8. 项目当时命名 **milkrun**（后更名，见 §3）。

## 2 · 一句话需求（当前态）

> 给普通用户的 AI 工具额度神器：以「带菜单栏界面的 MCP 服务」形态常驻本机，宿主 agent 一句话即可安装；自动完成各目标应用的每日签到与账号保活，宿主通过自身原生定时任务按自然语言计划调用 QKA，成功失败有日志、到账有确认；新目标应用靠插件体系（适配器热更新）扩展，本体低频发版。
>
> v1.1 补充的第二条主线：这个 MCP 服务必须是** agent 友好**的——每个目标应用是一个能力自描述的 agent，每次调用有机读的后果声明，每个结论有可核查的证据，任何变更能预演能诊断（FR-14/15/17、FR-8、NFR-8）。
>
> v1.2 的目标应用节奏：**V1 四个**——WorkBuddy CN、豆包工作、Qoder、Qoder CN；**V2 三个**——Trae、Trae CN、千问办公。账号保活也在 V1，但**只支持 WorkBuddy CN**：每天一次最低成本真实对话。WorkBuddy 国际版暂不做（用户 2026-10-28 明确）。登录态分“导入”和“受管”两类：导入来源严格只读，受管来源由 QKA 通过目标应用官方登录建立，并只按官方机制刷新。

| T4 | 命名 | milkrun → **QKA** | 用户认为 milkrun 过于抽象，点名 rea（rea-agents = Reverse Engineering Agents）的命名方式很直观；定稿 **QKA = Quota KeepAlive Agent**，kebab 全称 `quota-keepalive-agent` |
| T5 | logo | 两轮迭代 | 第一轮线稿方向被否（B 系「加对勾」被判「更丑」）；重启后改走「圆角底板 + 单一镂空」路线，定稿 **C4 心电线 + 保活绿 #0EA371**（保活语义），备选极光渐变/曜石黑 |
| T6 | 架构决策 | 三个分叉拍板 | ① 适配器运行时 = **Bun 子进程宿主**（npm 零移植）；② 与 magpie 社区签到插件**借鉴不绑定**（兼容层列 backlog）；③ **不上 Apple 开发者账号**（Gatekeeper 摩擦由 agent 安装自动清隔离化解）；调度/鉴权/凭据/日志/分发按先例默认值定稿 |
| T7 | 范围扩展 | 初始覆盖主流 | 用户要求「初始尽可能包括市面主流 agent，插件体系负责扩展」→ 首发集合扩为：确定首发 WorkBuddy CN + Qoder CN，**Trae CN、豆包列为首发候选（真机实测准入）**，MiniMax Code / ZCode / CodeBuddy 为 stretch；宿主侧主流 agent 配置写入全覆盖 |
| T8 | 需求优化 | **借鉴 rea 与 magpie**（v1.1） | 用户要求设计结合 rea 的「MCP 多工具」思路（本项目对应多 agent）与 magpie 的登录凭证、界面 UI、多环境打包、开发语言优点 → 补齐"宿主 agent 如何机读地知道 QKA 能做什么、动作有何后果、到账结论凭什么可信"，并把 magpie 已趟平的常驻工程细节写成可验收需求；同步明确**不吸收**的部分（见 §6） |
| T9 | 范围重定 | **V1 四个 / V2 三个**（v1.2） | 用户明确：V1 只做 WorkBuddy CN、豆包工作、Qoder、Qoder CN 四个签到领积分；V2 再补 Trae、Trae CN、千问办公。保活进 V1 但只做 WorkBuddy CN（每天发一条消息，参考 dsh `dsh-workbuddy-keepalive`）。同时明确：插件由用户自行开发可扩展；除对话配置外必须支持手动配置；同一目标应用可配多账号且都参与签到 |
| T10 | 命名与边界确认 | 豆包工作 / Qoder 双 App / CN 优先（v1.2） | 用户确认：① **豆包工作是独立产品**（不是豆包电脑版），当前有签到领积分活动；② **Qoder 与 Qoder CN 是两个独立 App，额度独立**；③ **WorkBuddy 目前先做 CN**，国际版本期不做；④ 实现顺序按 WorkBuddy CN → Qoder CN → Qoder → 豆包工作；⑤ Trae 国际版与旧调研冲突按推荐处置——若确认无签到活动则从 V2 移出，不做"仅账号管理" |
| T11 | 三张工单拍板 | 工具面 A / 插件折中 / 红点 + 每小时巡检（v1.3） | 用户确认：① 多 agent 取 **A**（agent 自描述对象、工具名常数级）；② 未签名插件取**折中**（只读用户当场指定的单个账号登录态，一次性、不入库、逐次确认并写审计）；③ 签到失败**菜单栏红点 + 点进去看详情**，默认不弹系统通知；④ **默认每小时巡检一次，当天签到成功即当天不再执行**——用高频巡检而不是单次成功来避免漏签 |
| T12 | 登录态与调度职责收敛 | 官方登录 + 宿主独占调度（v1.4） | 用户确认：① 添加账号应像 magpie 一样可手动触发目标应用**官方登录页**；QKA 不接收密码、验证码或扫码内容，只等待可信完成结果并做只读身份校验；② 导入来源永不刷新、不回写，受管来源只按官方机制刷新；③ 调度属于 agent 宿主，QKA 不创建、保存或修改定时任务，也不提供 `schedule_get` / `schedule_set` 或本地兜底定时器；④ 主窗口固定五栏：应用管理、日志、账号管理、Agent 接入、插件 |

## 4 · 功能需求清单（v1.4）

> 标记：**◆** 在 v1.0 基础上强化；**★** v1.1 / v1.2 新增；无标记者与 v1.0 同。

### 4.1 安装与接入

| 编号 | 需求 | 验收要点 | 设计 |
|---|---|---|---|
| FR-1 ◆ | 一句话安装 | 对宿主说「帮我装 QKA」→ skill 引导 agent 完成：下载校验、清 Gatekeeper 隔离、首启、写 MCP 配置、连通验证，并引导用户在宿主自身创建原生计划，全程小白无感。强化：**① 变更前给出只读预演计划**（改哪些文件、备份位置、如何验证、如何撤销）；**② 每宿主配置写入前备份且可回滚**；**③ 配对 token 按宿主区分、可单独吊销**；**④ 首次钥匙串读取的 macOS 授权框由 agent 引导用户完成并当场验证**。QKA 不保存或代注册宿主计划 | 05 |
| FR-6 ◆ | MCP 工具三面 | 不只 tools：**tools（稳定通用面 `agents_list`/`accounts_manage`/`checkin_run`/`status`/`plan_validate`/`log_tail`/`doctor_run`，`feed_list` 空占位；工具名清单不随目标应用数量增长）+ prompts（引导式工作流，如“在宿主中创建每小时计划”“添加账号并完成官方登录”“排查某账号失败”）+ resources（今日状态、agent 与登录态来源、日志游标、宿主接入指引可被宿主直接读取）**；HTTP 端点 + stdio 桥双接入。**不提供任何调度读写工具** | 01/04 |
| FR-13 ◆ | 主流宿主覆盖 | WorkBuddy、Codex、ZCode、Claude Code、OpenCode 等主流 harness 的配置写入支持——**任意支持 MCP 的 harness 都可通过对话调用 QKA 或让 QKA 完成接入**（不支持 MCP 的工具不在承诺内）。验收口径：每个宣称支持的宿主必须有一份配置档案（配置位置、HTTP/stdio 接入、token 写入、**宿主原生持久定时任务的创建与验证指引**、卸载方法）并在该宿主实测通过；只写进 `mcpServers` 不算覆盖。宿主计划不由 QKA 保存或代注册。注意 WorkBuddy **同时是宿主也是签到目标应用**，两种角色分别验收 | 05 |
| FR-14 ★ | 目标应用 agent 自描述 | 一个目标应用 = 一个可枚举的 agent，宿主可机读到它的**能力、所需钩子、账号与登录态来源列表、来源类型/健康/优先级、支持的操作、当前可用性与不可用原因**；适配器热更新后能力清单自动刷新；本体不得因某个 agent 长出专用分支（与 NFR-4 同向） | 01/02 |
| FR-15 ★ | 工具效应声明 | 每个 MCP 工具与每个 agent 动作携带**机读效应元数据**：是否触网、是否产生外部副作用、是否消耗额度、是否幂等、是否可能触发重新登录。宿主据此自动决定是否执行；**元数据缺失时按最保守处理** | 01/04 |
| FR-17 ★ | 一键诊断与预演 | `qka doctor --json` 输出检查项、结论、修复建议（安装态、配对、登录态来源可读性、最近一次宿主调用、适配器版本、端口占用）；安装、token 旋转、受管来源创建后的持久化、本体自更新等变更支持 dry-run 或可回滚计划。QKA 不伪装成能读取宿主内部计划，只报告“不可观察”，并给出该宿主的原生调度创建/核验步骤。**这是 FR-1「小白无感」的技术前提** | 01/05 |
| FR-19 ★ | 单二进制多形态与构建矩阵 | 同一二进制提供 `serve / tray / panel / bridge / tui / doctor / update / autostart` 形态；**无 GUI 形态可交叉编译**（darwin arm64/amd64、linux、windows 路径保留），GUI 形态因系统 webview 走原生构建；容器环境检测后禁用自更新。本期只交付 macOS，但需求固定"扩展形态与平台不改结构" | 01/05 |
| FR-20 ★ | 手动配置 | 不依赖任何宿主对话也能完成 QKA 侧全部关键配置：自动发现账号、手动添加并启动目标应用官方登录、指定已有登录态来源、设置来源优先级、添加/删除账号、逐账号启用签到/保活、改端口与隐私开关。面板是 QKA 本地配置的完整控制台，对话只是加速入口；**宿主内的定时计划不属于 QKA 配置**，面板只展示最近调用并给出在宿主中创建或核验计划的操作指引 | 00 |

### 4.2 核心业务能力

| 编号 | 需求 | 验收要点 | 设计 |
|---|---|---|---|
| FR-2 | 账号发现 | 自动检测本机已登录目标应用的账号（含多账号），面板展示并一键启用；用户也可“手动添加”启动目标应用官方登录，或显式指定一个已有登录态来源。QKA 不接收密码、验证码或扫码内容；官方登录返回后必须通过只读身份与能力校验才算成功 | 00/02 |
| FR-3 | 自动签到 | 每目标应用每日领取额度收益；当日幂等终态；活动未放量不算终态继续等 | 03 |
| FR-4 ◆ | 账号保活（V1 仅 WorkBuddy CN） | WorkBuddy CN 每日一次最低成本真实对话，维持账号活跃：发一条最小成本的真实对话请求并拿到真实回复才算完成；**单日最多成功一次**，失败后设置 10 分钟冷却门槛，不因此消耗当天次数；冷却结束后的真实重试仍由后续宿主或手动调用触发。成本按上游回执展示，最近一次真机实测为 0.02 积分，不写死历史估算。实现参考 dsh `dsh-workbuddy-keepalive`：走真实上游请求而非伪造心跳 | 02/03 |
| FR-5 ◆ | 宿主调度约定 | **调度权只属于宿主**：推荐宿主默认每小时调用一次 QKA，但计划由宿主按用户自然语言创建、保存和修改；QKA 不提供调度读写工具、不保存计划、不自行唤醒、没有本地兜底定时器。QKA 每次收到 `checkin_run` 只执行当次工作并做北京日界幂等；某账号当天成功后，后续调用不再对它发起领取。QKA 展示最近调用时间，供用户判断宿主计划是否仍在工作 | 03/05 |
| FR-8 ◆ | 到账确认（带证据） | 成功/失败均结构化返回（state/credits/balance），宿主对话与面板同步可见。强化：结果附**证据链**（触发时间、脱敏端点、上游返回码、前后余额差值、结论来源），并区分**观察 / 推断 / 未知**三态；**证据不足时不得宣称"已到账"**，只能报告"已领取待复核" | 03 |
| FR-12 ◆ | 多账号 | **同一目标应用可配置多个账号**，每个账号独立启停、独立登录态来源策略、独立状态与日志；一次宿主调用可以展开该目标应用下的多个启用账号并逐个执行，一个账号失败不影响其他账号；保活（WorkBuddy CN）同样按账号分别计算当天是否已完成 | 02/03 |
| FR-11 | 隐私开关 | per-目标应用 启用/停用，停用即零凭据读取 | 04 |
| FR-16 ★ | 凭据源与汇双向门控 | 隐私开关关闭时，**所有凭据读取路径与所有写入/上报路径同时短路**；期间 QKA 自身的受管来源存储**不读不写、原样保留**，重开即恢复；凭据位置 Keychain 优先、文件回退；系统拒绝授权后进入冷却。**导入来源永不刷新、不回写；受管来源只能按目标应用官方机制刷新**。QKA 不接收账密、验证码或扫码内容 | 04 |

### 4.3 可见性与常驻体验

| 编号 | 需求 | 验收要点 | 设计 |
|---|---|---|---|
| FR-7 ◆ | 菜单栏面板 | 主窗口固定五栏：应用管理、日志、账号管理、Agent 接入、插件；设置独立入口。账号页显示登录态来源类型/健康/优先级，Agent 接入页提供宿主原生定时任务创建指引与最近调用时间。**签到失败必须在菜单栏显示红点**，点进面板能看到目标应用、账号、来源类型、失败原因、已尝试次数、下一步（立即重试/重新登录/等宿主下一次调用）。默认不弹系统通知，系统通知作为可选项。界面契约：**默认 `LSUIElement` 纯菜单栏无 Dock 图标**（可动态开）；面板吸附托盘图标下方、Esc/失焦即隐、**不抢键盘焦点**、跟随全屏 Space；模板图标适配深浅色；**单实例身份以配置目录为准** | 00 |
| FR-18 ★ | 设置由声明生成 | 新增开关/选项不各自手写 UI：由配置结构生成表单并渲染，使"加一个隐私开关"的成本接近零；配置写入原子、带锁与备份 | 00 |

### 4.4 更新与运维

| 编号 | 需求 | 验收要点 | 设计 |
|---|---|---|---|
| FR-9 | 适配器热更新 | 市场索引 + ed25519 签名 + 启动/6h/手动拉取；失败回退上一版 | 02 |
| FR-10 ◆ | 自更新 | 官方源 feed + SHA-256 校验 + 旧版回滚，避开签到忙时。补工程细节：**更新经 listener 交接完成，常驻 MCP 端点不断连**；忙时等空闲再换 bundle；新版本首启或健康检查失败自动恢复 `qka.old`；重启路径含重试与落盘日志 | 05 |
| FR-21 ★ | 插件开发与本地加载 | 用户/第三方可自行开发适配器扩展支持的目标应用：提供 manifest 契约文档、可运行的适配器模板与脚手架、`qka adapter validate`（离线校验 manifest、能力、效应声明），本地未签名包仅在**显式开发者模式**下可加载并在面板标注"未验证"。**凭据边界采用折中方案**：未签名适配器不得继承全部凭据，只能读取用户当场为其指定的**单个账号、单个已有来源**；授权一次性、不缓存、不落盘；每次加载都弹确认（显示包名、来源类型/路径、目标应用与账号）并写审计日志。未签名插件不得创建受管来源。签名、市场发布与自动更新沿用 FR-9；本地开发包不进入自动更新通道 | 02 |

## 5 · 非功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| NFR-1 | 小白可用 | 用户不需要命令行知识；一切安装/排障由 agent 代办；中文界面文案。技术前提是 FR-17 的机读诊断与 dry-run |
| NFR-2 | 安全边界 | 导入来源只读、受管来源由 Keychain 加密保存且只按官方机制刷新；明文只在必要的内存调用链中出现，不落日志；状态文件 0600 原子写；端点三层校验；适配器签名 + 最小权限钩子 + 子进程隔离（详见 04） |
| NFR-3 | 可靠性 | 北京日界幂等键；每次宿主或手动调用都经过同一执行锁。签到失败等下一次宿主调用，不在 QKA 内自建小时内重试；单日成功后当日本账号不再领取；午前 provisional 午后只读复核；睡眠期间 QKA 不补跑，恢复后的首次宿主/手动调用再判断是否需要执行。保活失败有 10 分钟冷却门槛，真实重试仍由后续宿主/手动调用触发，最多当日成功一次（详见 03） |
| NFR-4 | 可演进 | 本体不含目标应用逻辑；适配器高频热更、本体低频发版；新工具接入 = 新 npm 适配器，本体零改动 |
| NFR-5 | 运维成本 | 无 Apple 证书运行；自更新安全边界明确为 SHA-256 + 官方源固定（magpie Windows 先例） |
| NFR-6 | 可审计 | 本机日志滚动保留 48 小时，一行一事件 |
| NFR-7 ★ | 环境友好 | QKA 不承担业务定时任务；仅更新检查、适配器拉取和冷却状态维护等后台循环采用对齐唤醒；菜单栏常驻有内存/CPU 预算目标值；端口被占用时识别 Docker/OrbStack 等转发器并**礼貌退让**，绝不杀他人进程 |
| NFR-8 ★ | 机读与有界输出 | 所有 CLI 子命令支持 `--json` 且输出 schema 稳定；任何子进程/工具的 stdout+stderr **有界截断、超限即拒**——否则宿主 agent 的上下文会被 QKA 撑爆 |

## 6 · 明确不做（本期边界）

- **活动/优惠情报 feed 的建设**（生产端与消费端）——仅留接口占位；用户明确「暂时不做，后续再加」。
- **Windows 平台**——适配器契约不变，后续补本体钩子。
- **无签到活动的工具**（iFlow、通义灵码、文心快码、Kimi——持续观察）。Trae 与 Trae CN 已进 V2 范围；其中 Trae 国际版若实测确认无签到活动，则从 V2 移出（不保留"仅账号管理"）。
- **WorkBuddy CN 之外的保活**（Qoder、Qoder CN、豆包工作、Trae、Trae CN、千问办公本期不做保活，只做签到）；**WorkBuddy 国际版**本期不做。
- **自有账密登录**——QKA 不收集、不保存密码、验证码或扫码内容；只允许启动目标应用官方登录页，等待可信完成结果并做只读身份校验。
- **编码实现**——本阶段产出为设计文档套件；实现另起阶段。

### 6.1 借鉴时明确不吸收（v1.1）

| 不吸收项 | 来自 | 理由 |
|---|---|---|
| **每目标应用一组动态工具名**（把"多 agent"实现为 `workbuddy_checkin`、`qoder_checkin`…） | rea 的 207 工具面 | ① 宿主缓存 `tools/list` 后适配器热更新会失配；② 本体被迫长出 per-app 分支，直接违背 NFR-4；③ 工具面从常数膨胀到 6×N，宿主决策更困难。rea 有 207 工具是因为逆向本身就是 207 种取证动作；QKA 的有效动作只有“管理账号/来源、跑一次、查状态、看日志”。**多 agent 改为 FR-14 的自描述对象**表达 |
| LAN 共享、命名 API key 与 IP allowlist | magpie 网关 | 本期只监听 loopback、不存在远程控制需求，引入即扩大攻击面 |
| iframe 沙箱插件页面 | magpie 插件页 | QKA 面板由本体承担，无第三方页面注入需求 |
| codesign `--verify` + team id 一致性校验 | magpie 更新链 | 与 T6「不上 Apple 开发者账号」冲突；NFR-5 已把边界定为固定官方源 + SHA-256 |
| 20 语言 README / 多语言文档 | rea | 本期 NFR-1 只承诺简体中文界面文案 |
| DPAPI / Secret Service 等跨平台凭据实现 | magpie | Windows 不在本期（§6），仅保留 FR-19 的构建路径 |

> 若你仍要求"真·多 agent 多工具"，则需追加承诺：工具清单变更主动通知 + 宿主端重取机制，并据此改写 FR-14。当前按上述推荐口径落文档。

## 7 · 需求内部张力与结论（已收敛）

1. **FR-1「全程无感」 vs FR-16 钥匙串授权**：首次读取 macOS 钥匙串必然弹系统授权框，无法由 QKA 静默跨过。结论：把它写进 FR-1 验收，由 agent 引导用户完成授权并当场验证；拒绝时进入冷却，不伪装成无感。
2. **FR-4 保活 vs 目标“领额度”**：保活是净消耗（最近一次真机实测 0.02 积分，实际以上游回执为准），服务的是“账号不掉线”而非“多领额度”。面板与返回中同时展示本次成本与当前余额，用户可自行关闭保活。
3. **FR-5 宿主调度能力**：已按用户实测收敛。WorkBuddy、Codex、ZCode、Claude Code、OpenCode 均支持 1 小时粒度计划；计划仍在各宿主原生调度中创建和保存，QKA 只接收调用。宿主若无法创建计划，可以手动调用 QKA，但自动签到没有生效，界面必须如实说明。
4. **FR-3 V1 四个目标应用 vs 单次可交付**：四个目标应用的凭据与协议不同，任一家的风控变化都可能拖住整体发布。结论：V1 内部按“引擎 → WorkBuddy CN → Qoder CN → Qoder → 豆包工作”分批工程验收；目标应用真机准入证据已齐，全部 M1/M2 验收通过后才对外宣称产品 V1 完成（见 06/05）。
5. **FR-20 手动配置 vs FR-16 登录秘密边界**：用户能手动添加账号，但 QKA 不自建账密表单。手动添加会打开目标应用官方登录页；用户只在该官方界面完成账密/验证码/扫码，QKA 不接触这些内容。选择/指定已有来源、来源优先级、启停账号和隐私开关属于 QKA 本地配置。
