# 00 · 产品定义与 UI

> 状态：v1.4（2026-10-29）· **需求文档是本套设计的唯一需求基线**；本文件不改变其中已经确认的决策。承接 FR-1…FR-8、FR-11…FR-18、FR-20。

## 产品定位

**qka（Quota KeepAlive Agent，额度保活代理）**是给普通用户的本机额度保活工具：它常驻于 macOS 菜单栏，以 MCP 服务接入用户已有的 agent 宿主，自动完成目标应用的签到和保活，并让用户在菜单栏与宿主对话中看到结果。

- 全称 / 仓库与包名：`quota-keepalive-agent`；短名：`qka`
- 品牌色：保活绿 `#0EA371`；图标：C4 心电线，见 `logo/`
- 本期平台：macOS；Windows、活动/优惠情报生产端与自有账密登录均不在本期。qka 可启动目标应用官方登录，但不接收密码、验证码或扫码内容。

## 三件套与职责边界

| 组件 | 形态 | 对需求负责的职责 |
|---|---|---|
| qka 常驻应用 | Go + Wails v3 菜单栏应用 | MCP 服务、单次任务执行、账号与登录态来源、适配器管理、日志、面板；不持有业务定时计划 |
| agent 宿主 | ZCode、Claude Code、Codex、OpenCode 等 MCP 客户端 | 用户的自然语言入口、安装执行者和**唯一调度器**：在宿主自身创建并保存原生定时任务，到点调用 qka |
| harness skill | GitHub 分发的安装与操作 skill | 下载、首启、写入宿主 MCP 配置、引导创建/核验宿主原生计划、故障排查 |

这里的“宿主是调度器”是需求已确认的硬边界：计划只存在于宿主自身，qka 不保存、不导入、不修改时刻表，也不运行本地兜底定时器。qka 只在收到 `checkin_run` 时执行，并通过北京日界状态保证多次调用不会重复领取。

## 用户旅程

1. **安装**：用户对宿主说“帮我装 qka”。宿主先向 qka 取**只读预演计划**（下载什么、装到哪、改哪些宿主配置、备份与撤销方式），用户确认后 skill 下载校验产物、清除隔离属性、首启、写入该宿主**专属**配对 token 的 MCP 配置，并**引导用户完成必要的钥匙串授权**。随后用 `doctor_run` 验证 qka 连通性和可观察的登录态来源；宿主内部计划是否创建成功由 skill 在宿主界面中引导核验，qka 不假装能读取它。
2. **发现或添加账号**：qka 可自动发现本机已登录目标应用中的账号；“添加账号”也可打开目标应用官方登录页，返回后只读校验身份和可用动作。qka 不显示密码、验证码或扫码输入框，也不接触这些内容。面板分别展示账号、来源类型、来源健康度与“启用签到/保活”开关。
3. **在宿主中创建计划**：用户对宿主说“每小时检查一次”。qka 可提供该宿主的原生计划创建指引和推荐调用文本，但计划由宿主保存和执行；qka 不提供 `schedule_set`，也不会返回“已保存计划”的假状态。
4. **日常执行**：宿主原生计划调用 `checkin_run`。qka 为每个启用账号分别运行当天需要的签到和保活任务，返回到账、余额、失败原因、下一步与**证据链**。没有宿主调用时 qka 不自行补跑。
5. **查看与处理**：菜单栏面板和 MCP `status` / `log_tail` 展示今日状态、来源健康、余额、最近调用时间、日志与待处理问题；凭据失效时提示用户回目标应用重新登录，或通过官方登录建立一个受管来源。

## 菜单栏面板

```
❤ qka（绿=全部完成 / 黄=有待复核 / 红=有签到失败，点开看详情）
├─ WorkBuddy CN
│  ├─ 账号 A  签到 ✓ +20（已确认）· 保活 ✓ −0.02 · 余额 1,240
│  └─ 账号 B  待重登
├─ Qoder CN
│  └─ 账号 C  签到 ⏳ 已领取待复核 · 余额 2,050
├─ 豆包工作
│  └─ 账号 D  ✕ 签到失败（第 3 次）→ 失败原因 / 下一步 / 重试
├─ 日志（最近 30 天，可按目标应用和账号筛选）
├─ 立即全部执行（先给预演：将触发 N 个账号 × 操作，预计消耗 X 积分）
├─ 诊断（一键 doctor，把机读结论翻译成人话）
└─ 设置：目标应用开关 / 隐私 / 配对 token / 关于
```

- “立即全部执行”与宿主调用同一条执行链，仍遵守当天幂等；保活失败有 10 分钟冷却门槛，但必须由后续宿主或手动调用再次触发。
- **签到失败显示红点，点进去看到具体信息**：目标应用、账号、来源类型、失败原因、已尝试次数、下一步（等宿主下一次调用 / 立即重试 / 回目标应用或官方登录页重新登录）。默认不弹系统通知。
- 推荐宿主创建**每小时一次**的原生计划；某个账号当天签到成功后，当天不再对它发起领取请求。qka 只显示最近调用时间和该账号的日终状态，不展示虚构的“下次运行时间”。
- 状态文案区分“已确认到账”与“已领取待复核”，与 03 的证据纪律一致；到账、余额与保活成本都可见（保活是净消耗，见需求文档 §7 第 2 条）。
- 停用某目标应用后，qka 不再读取其凭据、不会在该应用下发起新执行；已保存的非凭据状态仅用于向用户说明历史结果。
- 颜色适配浅深主题；菜单栏使用 `qka-logo-template.svg` 单色模板。
- 面板、安装引导、状态说明与排障提示默认使用简体中文，用户不需要理解命令行或 MCP 术语。

### 主窗口信息架构

主窗口固定五个一级页签，避免把账号、应用和宿主接入混成同一层级：

1. **应用管理**：每个目标应用的启用状态、账号汇总、来源健康、今日到账/保活与最近调用时间。
2. **日志**：按目标应用、账号、操作和状态筛选。
3. **账号管理**：自动发现、官方登录添加、已有来源导入、来源优先级、逐账号启停与删除。
4. **Agent 接入**：已配对宿主、MCP 连通状态、宿主原生计划创建指引与最近调用时间。明确写“计划由宿主保存”，不提供 qka 时刻表编辑器。
5. **插件**：适配器市场、更新、签名状态、开发者模式和本地加载。

设置是独立入口，不占用一级页签。添加账号或指定已有登录态来源是账号管理页的首要动作，必须在无宿主对话时也可完成。

## 常驻界面契约（FR-7）

借鉴 magpie 已趟平的细节，这些是验收项而不是实现偏好：

- 默认 `LSUIElement` 纯菜单栏运行、无 Dock 图标；Dock 显示作为设置项动态切换。
- 快捷面板吸附在托盘图标正下方；Esc 或失焦即隐藏；**不抢键盘焦点**（macOS 用 non-activating 面板窗口），用户正在打字时打开面板不打断输入；跟随全屏 Space。
- 菜单栏图标使用系统自动着色的模板图（单色 glyph），自适应深浅色与不同菜单栏底色。
- **单实例身份以配置目录为准**（不是可执行文件路径），因此同一份配置不会被两个进程同时写；跨目录多实例是有意为之。
- 退出与"更新后重启"的可靠性、休眠唤醒后的恢复见 05。

## 设置由声明生成（FR-18）

- 设置项由配置结构生成表单并渲染，新增一个开关不需要为新开关写界面代码；配置写入走文件锁 + 原子替换 + 备份。
- 隐私类开关在面板与 MCP 两侧呈现同一状态，默认值即最保守值（新目标应用默认停用，未确认前不读凭据）。

## 版本与范围

| 版本 | 目标应用 |
|---|---|
| **V1（四个）** | WorkBuddy CN（签到 + 每日一次真实对话保活）、Qoder CN（签到）、Qoder（签到）、豆包工作（签到） |
| **V2（三个）** | Trae、Trae CN、千问办公 |
| Stretch / 社区插件 | MiniMax Code、ZCode、CodeBuddy；由 FR-21 的插件开发能力承接 |
| 宿主覆盖 | WorkBuddy、Codex、ZCode、Claude Code、OpenCode 等；每个宣称支持的宿主都必须有可验证的安装配置档案，见 05 |

保活只在 V1，且只做 WorkBuddy CN；其他目标应用只做签到。V1 内部按 WorkBuddy CN → Qoder CN → Qoder → 豆包工作 推进，四个全部通过才对外宣告 V1 完成（详见 06）。WorkBuddy 国际版本期不做；Qoder 与 Qoder CN 是两个独立 App、额度独立。

**手动配置是完整入口（FR-20）**：面板里可以自动发现账号、启动官方登录添加账号、指定已有登录态来源、调整来源优先级、删除账号、逐账号开关、改端口与隐私，不需要先有宿主对话；对话只是更快的路径。宿主原生定时计划属于宿主，面板不保存也不修改它。

每个目标应用在 qka 内是一个**自描述的 agent**（FR-14）：宿主可枚举它的能力、账号、支持的操作、后果声明与当前可用性；接入新目标应用不会改变 MCP 工具名清单（理由见需求文档 §6.1）。

**WorkBuddy 是双角色**：它既是可以调用 qka 的宿主，也是要被签到和保活的目标应用（CN 版）。两种角色在面板里分开展示（"作为宿主已接入"/"作为目标应用已启用"），实现上也走两条不同的代码路径。
