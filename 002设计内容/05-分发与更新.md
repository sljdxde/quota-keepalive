# 05 · 分发与更新

> 状态：v1.4（2026-10-29）· 落实 FR-1、FR-5、FR-10、FR-13、FR-17、FR-19、NFR-1、NFR-5、NFR-8。

## 已确认的分发决策

本期**不购买 Apple 开发者账号，不做签名和公证**。首启时可能被 Gatekeeper 拦截；QKA 的分发模型以 harness skill 代为执行安装、清理隔离属性和连通验证，降低普通用户的操作门槛。

这项决策的更新信任边界是：固定官方源 + 每个资产 SHA-256 校验 + 可回滚旧版。它校验下载内容是否与官方 feed 中的预期哈希一致，不宣称提供 Apple code-signing 身份链；这正是 NFR-5 所要求的明确边界。

## 首版安装链路

1. **产物**：GitHub Releases 提供 `QKA-<ver>-darwin-<arch>.tar.gz`、`SHA256SUMS` 和官方 `feed.json`；归档含 QKA 主二进制（一个二进制含全部形态，见 01）、Bun 运行时与图标资产。构建矩阵本期交付 macOS 双架构，同时保留 `linux`、`windows` 的无 GUI 交叉编译路径（FR-19）。
2. **预演（FR-17）**：agent 先取 dry-run 计划——将下载什么、装到哪个路径、改写哪些宿主配置、各自备份在哪、如何验证、如何撤销。用户确认后才执行。**这是"小白无感"的技术前提**：agent 能机读地知道下一步会发生什么，才敢代用户动手。
3. **install.sh**：检测 `arm64` / `x86_64`，从固定官方源下载并校验 SHA-256，安装到 `~/Applications/QKA.app` 或 `~/.qka/bin`，清理 quarantine 后首启 `qka serve`。首次安装优先使用 `43189`，被占用时在 `43189-43299` 中顺序选可用端口并写入私有 `endpoint.json`；skill 用实际端点配置宿主。运行中的已有实例不静默换端口，冲突时礼貌报告并给出显式重配路径，绝不杀他人进程（NFR-7）。
4. **宿主配置档案**：skill 检测已安装宿主，为每个宿主选择一个配置档案。档案必须声明 MCP 配置位置、HTTP 或 stdio 接入方式、**该宿主专属 token 的写入方式**、**在宿主自身界面创建原生定时任务的步骤**、推荐的每小时调用文本、计划核验方法、验证命令和卸载方法。每份配置写入前备份原文件，写入后验证，失败回滚；QKA 不保存或代注册计划。
5. **凭据授权引导（FR-16）**：首次读取钥匙串会弹 macOS 系统授权框。skill 必须把它当成**安装步骤之一**而不是意外事件：提示用户点允许、随后用 `doctor_run` 验证凭据确实可读；被拒则说明后果并给出重试路径。
6. **验证**：安装成功的最低标准是 QKA 健康、MCP 已配对、一次 `status` 调用成功、一个目标应用的账号/来源发现可用；skill 再在宿主界面中引导用户创建并核验原生计划。QKA 的 `doctor_run` 只检查 MCP 连通与最近调用，不能读取宿主内部计划。

“支持某宿主”不是只写进 `mcpServers`：只有配置档案在目标宿主上通过上述验证，才可计入 FR-13 的覆盖范围。

## 诊断命令（FR-17）

`qka doctor --json` 固定检查项，输出 `check / verdict / detail / fix`，schema 稳定（NFR-8）：

- 安装态与版本、 quarantine 是否残留
- 端点健康、端口占用者身份
- 每宿主配对状态与 token 有效性
- 每个目标应用的凭据可读性（含钥匙串授权被拒后的冷却状态）
- 最近一次宿主/手动调用时间与新鲜度；宿主内部计划状态返回 `not_observable`
- 适配器版本、签名校验结果、效应声明完整性（缺失即告警）
- 状态文件权限与可写性

skill 的排障话术全部建立在该输出之上，而不是让 agent 猜——这是 NFR-1 的落点。

## 自更新

- QKA 从固定官方源读取 stable `feed.json`，对选中资产做 SHA-256 校验；镜像若存在，只能替换下载前缀，不能替换 feed 中的版本和哈希。
- **不断连交接**：新版本进程接管旧进程的 listener 与在途连接，再移交托盘与面板，使常驻 MCP 端点在升级期间不出现"宿主连不上"的空窗（FR-10）。这是 magpie 已趟平的路径。
- 更新在没有正在运行的签到或保活任务时执行（忙时等 idle）；下载、校验、解压、健康检查均完成后才进行 bundle swap。自更新同样提供 dry-run 计划。
- 旧版本保留为 `qka.old`；新版本首启或健康检查失败时自动恢复旧版，并写入本机更新日志。重启路径含重试与落盘日志（系统休眠/锁屏时的重启失败要靠重试兜住）。
- 容器环境检测后禁用自更新（FR-19）。
- 适配器更新独立于本体更新，按 [02-适配器契约](02-适配器契约.md) 的市场签名和回退规则执行；目标应用规则变化不应强迫本体发版。

## 里程碑与公开验收

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 引擎 | serve、菜单栏、MCP 三层校验与三面（tools/prompts/resources）、agent 自描述注册表、效应声明、状态机与证据链、通用能力层、`doctor`、**WorkBuddy CN（签到+保活）+ Qoder CN（签到）** | 两个目标应用可发现多账号，能单次签到，WorkBuddy CN 能单次保活，结果与证据进入面板、日志和 MCP 返回；`agents_list` 与 `doctor_run` 可被宿主机读 |
| M2 可交付 V1 | 安装 skill（含 dry-run、配置备份回滚、钥匙串授权引导）、宿主配置档案、per-宿主 token、**宿主原生计划创建指引**、声明式设置、隐私完善、账号与来源管理面板、**Qoder 与豆包工作适配器、插件开发套件** | 四个 V1 目标应用在多账号下均可签到；WorkBuddy CN 保活可用；不依赖宿主对话也能完成 QKA 侧全部配置；用户在宿主内创建计划后可按小时调用；第三方可写一个本地适配器并被校验加载 |
| M3 运营基础 | 本体自更新（不断连交接）、市场索引、适配器签名热更新、构建矩阵发布、feed 占位 | 适配器规则变更可热修；升级期间宿主不感知断连；本期 `feed_list` 仍只返回空集 |

M1 是技术核心，不单独对普通用户宣称“可一键自动签到”；满足 FR-1 和 FR-13 的可发布 MVP 是 M1 + M2。**V1 的完成定义是四个目标应用全部通过验收，而不是 M2 的代码写完**（V1 内部顺序见 06）。V2（Trae、Trae CN、千问办公）不进本期里程碑。
