# 01 · 整体架构

> 状态：v1.4（2026-10-29）· 依据：[需求文档](需求文档.md) FR-1 至 FR-21、NFR-1 至 NFR-8。

## 组件图

```
┌─ agent 宿主（ZCode / Claude Code / Codex / OpenCode …）────┐
│ 自然语言入口 + 唯一调度：宿主原生计划 → MCP checkin_run        │
│ HTTP mcpServers，或 stdio → qka bridge                       │
└────────────────────────┬───────────────────────────────────┘
                         │ 配对 token
                         ▼
┌─ QKA 常驻应用（Go + Wails v3）──────────────────────────────┐
│ MCP 服务 / 单次执行协调器 / 账号与登录态来源 / 日志           │
│ 菜单栏面板（无业务定时器）                                     │
│ SQLite：任务状态、来源映射、日志；0600 原子状态文件：恢复快照 │
└──────────────┬───────────────────────────┬─────────────────┘
               │ stdio JSON-RPC             │ 受限本体钩子
               ▼                            ▼
┌─ Bun 适配器子进程 ────────┐      ┌─ 通用系统能力层 ─────────┐
│ 账号发现 / 签到 / 保活     │      │ 凭据访问 / HTTP / 存储    │
│ npm 包 + manifest + 签名   │      │ Keychain 与本地文件读取   │
└──────────────┬───────────┘      └──────────────────────────┘
               ▼
       目标应用开放接口
```

### 三个运行角色

- **宿主**持有唯一调度职责。它在自身产品中创建并保存原生持久任务，到点调用 QKA；QKA 不保存计划，也不参与宿主的注册状态。
- **QKA**持有“这次调用能否执行”的职责：展开账号与任务、检查日界幂等和冷却、原子抢占执行权、记录结果并返回统一结构。
- **适配器**持有“如何同目标应用交互”的职责：发现账号、组织签到/保活协议、解析结果。它不拥有跨目标应用的调度、认证、日志或状态规则。

调度与执行是两个独立职责：没有宿主调用就没有业务执行；任何一次调用都不会让 QKA 在本地创建下一次调用。

## 稳定 MCP 工具面

工具名是**常数级通用面**，不随目标应用数量增长：每接入一个新目标应用，增加的是一个自描述 agent 对象（见下节），不增加 `workbuddy_checkin` 这类专用工具名。理由见需求文档 §6.1。

| 工具 | 输入重点 | 结果与语义 |
|---|---|---|
| `agents_list` | 可选目标应用 | **列出全部目标应用 agent 的自描述**：能力、所需钩子、账号、支持的操作、当前可用性与不可用原因（FR-14） |
| `accounts_manage` | 目标应用、账号或来源、动作（发现、开始官方登录、导入已有来源、调整优先级、启停、删除） | 管理账号与登录态来源；不接收账密、验证码或扫码内容，删除 QKA 记录不删除目标应用数据 |
| `checkin_run` | 可选目标应用、账号、任务模式（默认执行当天应执行的任务）、宿主触发信息 | 每个账号 × 操作的结构化结果，含证据链；永远经过幂等、冷却和到账确认链 |
| `status` | 可选目标应用或账号 | 启用状态、今日签到/保活状态、来源健康、余额、待处理原因、最近一次调用时间；不包含 QKA 保存的计划 |
| `plan_validate` | 目标应用、账号、拟执行操作 | **只读预演**：若现在调用会触发哪些账号 × 操作、预计成本、冲突与后果，不产生外部请求（FR-15、FR-17） |
| `log_tail` | 筛选条件、游标、条数 | 最近 48 小时的一行一事件日志，不返回凭据；输出体量有上限（NFR-8） |
| `doctor_run` | 可选检查项 | 安装态、配对、登录态来源可读性、最近宿主调用、适配器版本、端口占用的机读结论与修复建议（FR-17）。宿主内部计划标记为“QKA 不可观察”，只给核验指引 |
| `feed_list` | 无 | 本期固定返回空集和“未实现”状态，不拉取活动或优惠情报 |

工具面中**没有** `schedule_get`、`schedule_set`、`fallback_set` 或任何等价的计划读写能力。这是职责边界，不是待实现项。

## MCP 三面：tools / prompts / resources（FR-6）

- **tools**：上面的稳定工具面，是宿主唯一的执行入口。
- **prompts**：引导式工作流模板，把“该按什么顺序问”沉淀进 QKA 而不是散落在各家 skill 里。首发集合：`install_and_pair`、`add_account_with_official_login`、`setup_host_schedule`、`diagnose_failed_account`、`explain_today_results`。`setup_host_schedule` 只输出宿主自身创建计划的步骤和调用文本，不写 QKA 状态。
- **resources**：可被宿主直接读取的只读视图——`qka://status/today`、`qka://agents`、`qka://accounts`、`qka://logs?cursor=`、`qka://host-integration`。没有 `qka://schedule`。

HTTP 使用 streamable HTTP；只支持 stdio 的宿主通过 `qka bridge` 转发到同一端点。

## 端点与多实例

- 默认端点为 `http://127.0.0.1:43189/mcp`，实际端点写入当前配置目录的私有 `endpoint.json`；宿主配置只引用实际端点。
- 首次安装若 `43189` 被占用，可在 `43189-43299` 中顺序选择第一个可用端口并持久化；skill 把实际端点写入对应宿主配置。
- 已经配对后的后续启动若端点被占用，QKA 不静默换端口，否则现有宿主配置会失效；它报告冲突并给出“显式重配宿主”的修复步骤，绝不结束占用进程。
- 单实例身份以配置目录为准：同一配置目录只跑一个 QKA；不同配置目录可并行，但必须使用不同端口、token 和数据存储，并在 UI 中明确当前目录。

## 工具与动作的效应声明（FR-15）

每个工具与每个 agent 动作在 schema 元数据里携带机读效应位，宿主据此自动决定是否执行、是否需要先问用户：

| 效应位 | 含义 | 例 |
|---|---|---|
| `accessesNetwork` | 是否发出本机以外请求 | `checkin_run` 是；`status` 否 |
| `mutatesTarget` | 是否改变目标应用侧状态 | 签到、保活是；复核只读否 |
| `spendsCredits` | 是否消耗额度 | WorkBuddy CN 保活是（最近一次实测 0.02，按实际回执展示） |
| `idempotent` | 同日重复调用是否等价 | `checkin_run` 通过本地日界门保证最多成功一次；`accounts_manage` 的官方登录和删除不是幂等动作 |
| `mayRequireReauth` | 是否可能触发重新登录提示 | 凭据失效时是 |
| `mutatesLocalState` | 是否写本机状态文件 | 结果落库是 |

**元数据缺失或不可知时，宿主必须按最保守取值处理**；QKA 自身的实现也按该规则回退，绝不把未知当成无副作用。

本期六个效应位足以覆盖 V1 动作。未来若出现“可能产生长期凭据”“可能修改目标应用设置”等新后果，必须通过向后兼容的 manifest schema 版本追加效应位，不在本图范围内预造空字段。

## 关键领域对象

- **目标应用 agent**：一个目标应用在 QKA 内的自描述身份，由适配器提供、本体统一封装后对外暴露。它的生命周期与适配器版本绑定，宿主可通过 `agents_list` 或 `qka://agents` 枚举。
- **登录态来源**：某个目标账号取得访问能力的一处来源，分 `imported` 与 `managed`。导入来源永不刷新、不回写；受管来源由 QKA 通过目标应用官方登录建立，只按官方机制刷新。一个账号可有多个来源，但一次执行只选一个。
- **来源优先级**：同一账号内选择来源的确定性规则，默认“用户显式固定 > 健康受管来源 > 健康导入来源”；每次结果记录实际使用来源。
- **每日操作**：一个账号在一个北京日界内的 `checkin` 或 `keepalive`。两种操作独立计状态，WorkBuddy CN 的保活不能被签到结果覆盖。
- **调用快照**：宿主或用户手动触发的一次 `checkin_run`。QKA 记录调用方、时间、结果和“自上次调用后经过多久”，但不把它解释成宿主计划是否真实存在。
- **执行租约**：一次调用在有限时间内独占一个每日操作。多个宿主或手动按钮并发到达时，只有取得租约的一方能发起外部请求。

## 单次执行生命周期

1. 宿主原生计划或用户手动按钮触发 `checkin_run`，并标记调用方。
2. QKA 依据目标应用、账号、操作类型和北京时间日界创建或读取每日操作；原子取得执行租约，退避中的操作直接返回当前状态。
3. QKA 调用适配器 `accounts.discover` 或使用已发现账号，随后将单个 `checkin.run` / `keepalive.run` 请求交给适配器。
4. QKA 按来源优先级选择一个健康来源；适配器只通过本体钩子取得当前调用可用的凭据引用，发出受控 HTTP 请求并返回标准结果。
5. QKA 在同一状态链里写入结果、日志和面板状态；成功但仍需午后确认的签到进入 `provisional`，不再重复领取而只走复核。
6. MCP 返回每个账号 × 操作的 `state`、`credits`、`balance`、时间、可读说明与**证据链**（见 03），供宿主对话和面板同步展示；证据不足时结论停在“待复核”，不写成“已到账”。

## 技术栈与目录

- 本体：Go 1.26 + Wails v3 + SQLite（`modernc.org/sqlite`）；TUI 是可后置的 `qka tui`。
- MCP：`modelcontextprotocol/go-sdk`。
- 适配器宿主：随应用打包的 Bun 1.4.x，以子进程和 stdio JSON-RPC 运行普通 npm 包。
- 前端：内嵌的零构建纯 JS，不引入大型框架。

## 单二进制多形态与构建矩阵（FR-19）

同一二进制承担全部形态，避免"装了两个程序互相抢端口"：`qka serve`（网关+托盘）、`qka tray`（仅菜单栏）、`qka panel`（只弹面板）、`qka bridge`（stdio→HTTP）、`qka tui`、`qka doctor`、`qka update`、`qka autostart on|off`。

- **GUI 形态**经系统 webview 需原生构建：macOS 本期交付（`darwin/arm64`、`darwin/amd64`）。
- **无 GUI 形态**用 `CGO_ENABLED=0` 交叉编译，保留 `linux`、`windows` 产物路径，使"移植平台"是发布工程问题而非结构问题——本期不承诺 Windows 可用，只承诺不改架构即可产出。
- 容器环境检测后禁用自更新与托盘。
- 所有子命令支持 `--json`，输出 schema 稳定；对子进程 stdout/stderr 做有界累积、超限即判失败（NFR-8）。

## 环境友好（NFR-7）

- QKA 不承担业务定时任务；仅更新检查、适配器拉取和冷却状态维护等维护循环采用**对齐唤醒**。
- 端口被占时先识别占用者（区分 Docker/OrbStack 等转发器），**礼貌退让并在面板与 `doctor_run` 中报告**，绝不结束他人进程。
- 常驻预算目标值：托盘空闲态内存与 CPU 上限在 M1 定基准、M2 回归。

```
quota-keepalive-agent/
├── cmd/qka/            # serve / tray / panel / bridge / tui / doctor / update / autostart
├── internal/
│   ├── mcpserver/      # MCP tools/prompts/resources、效应声明、配对与协议适配
│   ├── engine/         # 每日操作状态机、租约、退避、复核
│   ├── adapterhost/    # Bun 生命周期、JSON-RPC、版本切换
│   ├── capabilities/   # 通用凭据、HTTP、状态和日志能力
│   ├── agentreg/       # 目标应用 agent 自描述注册表（适配器能力的对外视图）
│   ├── accounts/       # 账号、来源类型/优先级、官方登录会话与健康状态
│   ├── feed/           # 适配器市场索引、签名校验、热更新
│   ├── store/          # SQLite 与 0600 恢复快照
│   └── gui/            # 托盘与内嵌前端
├── adapters/           # 独立发布的官方 npm 适配器源
├── skill/              # 安装与宿主配置 skill
└── scripts/            # install.sh / feed 构建
```

本体不放 WorkBuddy CN、Qoder、Qoder CN、豆包工作等目标应用的业务分支；若某适配器发现通用能力缺失，应新增可复用、版本化的能力契约，而不是偷偷把目标逻辑塞回本体。
