# 06 · 目标应用路线图

> 状态：v1.4（2026-10-29）· 区分“被签到的目标应用”和“调用 QKA 的宿主”，避免把两类扩展混为一谈。每个目标应用在 QKA 内是一个自描述 agent（FR-14），准入条件因此包含“能如实声明能力与后果”。
>
> 版本节奏：V1 四个（WorkBuddy CN、豆包工作、Qoder、Qoder CN），V2 三个（Trae、Trae CN、千问办公）。保活只在 V1，且只做 WorkBuddy CN。宿主独占调度，QKA 只执行被调用的任务。

## V1 目标应用（macOS）

| 目标应用 | 能力 | 状态 | 准入 / 风险 |
|---|---|---|---|
| WorkBuddy CN | 多账号发现、签到、每日一次最低成本真实对话保活 | ✅ V1 必做 | 签到与保活独立验收；保活按当次回执展示实际成本，最近一次实测 0.02 积分；**国际版本期不做** |
| Qoder CN | 多账号发现、签到 | ✅ V1 必做 | 每日活动在 10:00 后可用、活动 id 变化、领取幂等（dsh-qoder-checkin 现成参考） |
| Qoder | 多账号发现、签到 | ✅ V1 必做 | 与 Qoder CN 是**两个独立 App、额度独立**：独立适配器、独立凭据路径与接口；需实测国际版活动是否可领取 |
| 豆包工作 | 多账号发现、官方登录、签到 | ✅ V1 必做 | 独立产品；个人账号真实签到并到账 `200 POINT`；同日重复调用未重复发奖但返回 `710010702 / 系统错误`，`idempotent` 保持 `false`，由本地日界锁保证同日成功一次 |

一个目标应用可以进入 V1，必须同时满足：能发现本机已登录账号，或能通过目标应用官方登录建立受管来源；QKA 不收集任何登录秘密；导入来源只读、受管来源只按官方机制刷新；可区分成功、未放量、可重试失败和需重登；结果可回到 QKA 的统一状态与日志模型；**能给出完整且如实的效应声明（FR-15）与到账证据（FR-8）**——缺效应声明的动作按最保守处理，等于不可自动执行。

V1 的目标应用真机准入证据已经齐全，详见[目标应用真机实测与准入结论](../.scratch/wayfinder/research/target-apps-live-test.md)。实现顺序仍为 **WorkBuddy CN → Qoder CN → Qoder → 豆包工作**；对外 V1 完成还需要 M1/M2 工程验收，不以本路线图代替。

## V2 目标应用

| 目标应用 | 能力 | 状态 | 准入 / 风险 |
|---|---|---|---|
| Trae | 多账号发现、签到 | 🧪 V2（条件保留） | 国际版签到活动与凭据路径待调研；**若确认无签到活动，则从 V2 移出**（不做"仅账号管理"——QKA 的产品目标是签到与保活） |
| Trae CN | 多账号发现、签到 | 🧪 V2 | 真实设备号 + ECDSA 设备签名（一设备一天一账号）；magpie 内置 `trae_checkin.go` 可作参考 |
| 千问办公 | 多账号发现、签到 | 🧪 V2 | 尚未调研：产品形态、凭据位置、是否有签到活动均待确认，不能默认存在 |

V2 的前置是 [目标应用真机实测](../.scratch/wayfinder/010-trae-doubao-live-test.md) 扩大范围后的版本：它负责 V1 的豆包工作 + Qoder 准入，并兼顾 V2 的 Trae/Trae CN/千问办公可行性。除原判定项外，实测需产出每个候选的 `manifest.actions` 效应声明与凭据读取路径（Keychain 优先或文件回退），供 02/04 落契约。

## 宿主覆盖

宿主不是签到对象。WorkBuddy、Codex、ZCode、Claude Code、OpenCode 等宿主通过 MCP 调用同一个 QKA；它们的覆盖由 05 的“宿主配置档案”验收，而不是由目标应用适配器验收。

**WorkBuddy 是双角色**：作为宿主，它可以通过对话调用 QKA；作为目标应用，WorkBuddy CN 的账号要被签到与保活。两个角色分别实现、分别验收，不共用一套代码路径。

- HTTP MCP 宿主直接使用 loopback 端点和配对 token。
- 仅支持 stdio 的宿主通过 `qka bridge` 接入同一端点。
- 宿主原生计划的创建、保存、修改和运行都属于宿主；QKA 只提供推荐调用文本、宿主侧步骤和最近调用时间。
- 无法持久创建计划的宿主仍可安装并手动调用 QKA，但不能被界面标记为“自动签到已启用”。

## Stretch 与暂缓

- 社区/用户插件探索顺序（不属于官方承诺）：MiniMax Code → ZCode → CodeBuddy，由 FR-21 的插件开发能力承接。
- 暂缓：iFlow CLI、通义灵码、文心快码、Kimi；当前未确认有适合自动化的签到活动。
- 不做：豆包的非桌面端签到形态。
- 后续平台：Windows；适配器业务契约保持不变，平台凭据能力另行设计。

## 扩展与 feed 边界

新目标应用的标准接入物是一个签名 npm 适配器和相应验收记录；它通过市场索引热更新，QKA 本体低频发版。对外表现是一个新的自描述 agent，MCP 工具名清单不变——这是"扩展靠插件体系"在 agent 侧的可验证含义（需求文档 §6.1 记录了为何不采用每应用一组工具名）。用户自研插件按 FR-21：模板 + `qka adapter validate` + 开发者模式本地加载，发布仍走签名市场。

“签到活动检索 / 优惠活动检索”本期不建设生产端或消费端。仅保留 MCP `feed_list` 的空集占位，后续若重开该范围，必须另立 Wayfinder 地图和需求，不得把远端情报抓取混入签到适配器。
