# 区分受管与导入登录态

QKA 需要支持同一目标应用的多个账号，同时避免破坏目标应用自己的登录状态。我们决定把目标账号与登录态来源分开，并只允许 QKA 刷新通过目标应用官方登录流程建立、明确标记为受管的来源；从目标应用当前状态读取的导入来源始终只读，不刷新、不回写。QKA 不接收密码、验证码或扫码内容；添加账号只启动厂商官方登录，并在返回后做只读身份校验。这样既能支持没有原生多账号能力的目标应用，又不会让 refresh 轮换把目标应用挤下线。

## Considered Options

- 只允许导入目标应用当前登录态：隔离最安全，但 Qoder 等单登录态应用无法满足多账号需求。
- 所有来源都由 QKA 刷新：能力完整，但会与目标应用争抢轮换型 refresh token，可能导致用户原有客户端掉线。
- 受管来源由 QKA 刷新、导入来源只读：多一条登录入口和状态模型，但能明确责任与失败边界。

## Consequences

QKA 必须解释受管与导入两类来源的差异，并在 UI、日志和返回值中显示实际使用来源。官方登录完成必须可验证，关闭页面不等于成功。删除 QKA 账号不能删除目标应用的数据。旧“QKA 永不刷新登录态”的安全表述必须收窄为“永不刷新导入登录态”。
