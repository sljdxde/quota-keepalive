# WorkBuddy CN MVP 只走 Magpie 浏览器登录并接受应用内签到兜底

WorkBuddy 5.6 及以后把桌面登录态加密保存，Magpie 无法读取；Magpie 的浏览器登录则使用腾讯官方页面取得可刷新的 OAuth 来源。同时，Magpie 的 WorkBuddy 签到请求不携带目标应用安全 SDK 生成的设备令牌，签到接口可能以 401 拒绝，而余额查询仍然成功。为尽快交付一个真实、可信的最小账号闭环，我们决定 MVP 只支持 WorkBuddy CN 的 Magpie 浏览器官方登录，并把该来源登记为 `managed`；桌面登录导入和 API key 暂不进入 MVP。账号启用前必须通过只读验证：余额或账号能力查询返回 2xx，且本地 uid/domain 与查询结果一致；验证阶段不得调用签到接口。首次发现的账号默认停用，已有账号状态保持不变。

签到只可宣称成功于 `claimed` 或 `done` 且有可核查证据。若签到请求返回 401、但余额查询成功，则记录为应用内签到兜底，引导用户在 WorkBuddy 官方 App 完成签到，再由只读状态检查确认结果；不得把该路径表述为自动签到成功。同一天已确认或已进入应用内签到兜底的账号不重复发起领取。MVP 不采用桌面 token 解密、目标应用 UI 自动化或自造设备令牌；UI 暂不按冻结原型重做，只补必要的加载、错误、空状态和兜底提示。

## Considered Options

- 读取 WorkBuddy 桌面加密登录态：会复用现有 App 登录，但需要解密或调用应用私有能力，违背 Magpie 边界且更易失效。
- 使用 API key：接入简单，但无法读取可信余额，不能满足只读验证和到账证据要求。
- 等待自动签到完全可用再交付：闭环最强，但把账号管理修复绑定到未解决的安全设备令牌问题上。

## Consequences

原计划中的 WorkBuddy 桌面 `imported/read_only` 来源在 MVP 中延期；当前可用的浏览器来源是 `managed`。自动签到不是无条件承诺，产品必须明确区分“已自动领取”“今日已领取”和“请回官方应用签到”。若未来 WorkBuddy 提供稳定、官方的设备令牌或签到授权方式，可另立 ADR 扩展自动签到，而不改变账号与来源边界。
