## Problem Statement

普通用户会在多个 AI 应用里拥有账号和额度活动，但每天都要分别打开 WorkBuddy CN、Qoder CN、Qoder 和豆包工作，寻找可能每天变化的签到入口，并记得为 WorkBuddy CN 发一条对话来保活。同一应用有多个账号时，遗漏、重复操作和登录态失效更难管理。

已有插件只适合熟悉命令行的技术人员，不能作为面向普通用户的完整产品。用户需要在不理解 MCP、命令行、凭据格式或目标应用接口的前提下，通过自己已经在用的 agent 宿主完成安装、账号接入和每日自动执行；同时必须清楚知道哪个账号成功、是否真正到账、失败后该怎么办，以及登录秘密没有被 qka 收集。

## Solution

qka 是一个仅在 macOS 常驻的菜单栏应用，同时作为本机 MCP 服务供任意兼容宿主调用。用户对宿主说“帮我装 qka”，宿主按预演、备份、安装、配对、验证的顺序完成接入，并引导用户在各宿主自己的界面中创建每小时原生计划。宿主负责“何时调用”，qka 负责“这次能否执行、执行了什么、证据是否足以宣称到账”。

V1 支持 WorkBuddy CN、Qoder CN、Qoder 和豆包工作的签到；WorkBuddy CN 额外支持每天一次真实对话保活。用户既可自动发现已登录账号，也可在账号管理中手动添加：qka 打开目标应用的官方登录界面，用户只在厂商界面完成登录，qka 只等待完成结果并做只读身份校验。每个账号可拥有多个登录态来源，导入来源永远只读，受管来源仅按官方机制刷新。

主窗口固定为“应用管理、日志、账号管理、Agent 接入、插件”五个页签，设置使用独立入口。签到失败通过菜单栏红点和面板详情呈现。适配器通过签名 npm 包支持热更新和用户自研插件，使目标应用协议变化不必频繁发布 qka 本体。

## User Stories

1. As an ordinary user, I want to install qka by asking my agent host in natural language, so that I do not need command-line knowledge.
2. As a cautious user, I want to see a read-only plan of files and host configurations that will change before installation, so that I know what I am authorizing.

6. As a user with an HTTP MCP-capable host, I want qka to configure the host to call its loopback endpoint, so that my existing host can use qka without special integration code.
7. As a user with a stdio-only host, I want qka to expose a bridge to the same service, so that both transport styles have identical capabilities.
8. As a user with several agent hosts, I want each host to receive its own pairing credential, so that revoking one host does not break the others.
9. As a user, I want to revoke one host's pairing credential without affecting other hosts, so that a stale or compromised host can be removed safely.

## Implementation Decisions

1. **Platform and release scope.** V1 delivers macOS for both supported architectures. Target applications are WorkBuddy CN, Qoder CN, Qoder, and Doubao Work. WorkBuddy CN is the only target-application keep-alive integration. V2 target applications and platform ports must not delay or reshape the V1 architecture.

2. **Three-role architecture.** The host owns schedule creation, persistence, and execution. qka owns account/source management, daily-operation state, execution leases, evidence, logs, and UI. Adapters own target-application discovery, official-login descriptions, claim/keep-alive protocol, and result parsing. A host schedule calls the same execution operation as a manual UI action.

3. **Single application binary.** The Go + Wails v3 application exposes serve, tray, panel, bridge, TUI, doctor, update, and autostart modes from one binary. The desktop UI uses embedded zero-build JavaScript. The adapter runtime is packaged Bun, communicating over stdio JSON-RPC. SQLite is the source of truth for accounts, source mappings, daily-operation state, leases, and logs.

4. **Constant MCP surface.** The externally visible tools are exactly `agents_list`, `accounts_manage`, `checkin_run`, `status`, `plan_validate`, `log_tail`, `doctor_run`, and the empty `feed_list` placeholder. Adding a target application adds an agent descriptor and adapter, never a new per-application tool name.

5. **No scheduling interface.** No scheduling read/write/reset/fallback operation exists in tools, prompts, resources, adapter manifests, or persistence. `checkin_run` never creates a future invocation. “Last invocation” is an observation, not proof that a future host schedule exists.

6. **MCP prompts and resources.** Prompts cover installation and pairing, adding an account through official login, creating a schedule in the host, diagnosing a failed account, and explaining today's results. Read-only resources expose today's status, agents, accounts, cursored logs, and host-integration guidance. There is no schedule resource.

7. **Transport parity.** HTTP streamable MCP and the stdio-to-HTTP bridge expose the same tool/prompt/resource contracts and behavior. Bridge output must never echo pairing credentials.

8. **Endpoint selection.** The default endpoint is `127.0.0.1:43189/mcp`. A first install may choose the first free port in `43189-43299` and persist it. After pairing, a port conflict is an explicit error requiring host reconfiguration; qka never kills the occupant or silently changes the endpoint.

9. **Process identity.** One process owns one configuration directory. Different configuration directories may run concurrently only with distinct ports, pairing credentials, and databases. The active configuration directory is visible in the UI.

10. **Pairing security.** The HTTP server binds only to loopback, validates Host and any Origin, and requires a pairing credential. Each host gets a distinct credential; only a hash is stored locally. One host can be revoked independently. Revocation and rotation are explicit, previewable configuration changes.

11. **Target-application representation.** Each adapter is projected as one self-described target-agent object containing identity, version, capabilities, required hooks, supported operations, effect declarations, enabled/available state, unavailability reason, accounts, sources, health, preference, and last invocation time. The projection contains no hard-coded branch for a particular product.

12. **Effect declarations.** Every action declares all six effect positions:

    ```json
    {
      "accessesNetwork": true,
      "mutatesTarget": true,
      "spendsCredits": false,
      "idempotent": true,
      "mayRequireReauth": true,
      "mutatesLocalState": true
    }
    ```

    The declaration is part of signed adapter metadata and is the source of truth projected to the host. A missing or unknown field is surfaced conservatively and produces a doctor warning. `plan_validate` computes an aggregate effect preview without performing the action.

13. **Account/source separation.** A target account is independent from its login-state sources. One account may have several sources, but one execution selects exactly one. The default preference is explicit user pin, then healthy managed source, then healthy imported source. Every result records the selected source.

14. **Imported-versus-managed policy.** Imported sources are read-only. qka must never refresh, rotate, or write them. Managed sources are created only after verified official sign-in and may be refreshed only through the target application's declared official mechanism. Credential data for managed sources is stored in a qka-specific Keychain item; imported credentials remain in the target application's own storage.

15. **Official-login state machine.** The login outcome is machine-readable and only `verified` may create a managed source:

    ```text
    idle -> awaiting_user -> verified
                    |-> cancelled
                    |-> expired
                    |-> rejected
                    |-> pending
    ```

    `pending` is not success. `cancelled`, `expired`, and `rejected` create no source. `verified` requires a read-only identity query or equivalent no-side-effect validation of the target account and an available action.

16. **Official-login security boundary.** qka accepts only adapter-declared vendor HTTPS domains, signed app deep links, or the target application's own authorized window. It presents the target application, destination, purpose, timeout, and cancel action. It does not inject input, read password DOM, capture input, OCR, record keyboard or clipboard, or accept password, verification-code, or QR payload fields.

17. **Source failure behavior.** An imported source that becomes invalid is deactivated without refresh or write-back. A managed source may recover only through the official refresh path. If it cannot, it becomes “reauth required”. A source failure affects only its account/source group and never overwrites another application, account, or source.

18. **Per-account operation policy.** Check-in and keep-alive enablement are stored per account and operation. A target-application privacy switch gates every credential source and every sink: scanning, discovery, Keychain reads, adapter dispatch, credential resolution, network requests, reports, and execution. While disabled, qka-managed credential records are neither read nor written and remain preserved.

19. **Beijing day key.** Every daily operation is keyed by target application, account, operation, and the Asia/Shanghai calendar date. The key is evaluated at invocation time. The host's own timezone must not alter the business day.

20. **Daily-operation state machine.** Check-in and keep-alive are independent state machines:

    ```text
    checkin:
      pending -> running(lease) -> signed_provisional -> signed_confirmed
                              |-> already
                              |-> none -> pending
                              |-> failed_retryable -> pending
                              |-> failed_final

    keepalive:
      pending -> running(lease) -> completed
                              |-> failed_retryable -> pending after cooldown
                              |-> failed_final
    ```

    `signed_provisional`, `signed_confirmed`, and `already` suppress another same-day claim. `none` means not released/available and remains pending for a later host call. `completed` suppresses another same-day successful keep-alive.

21. **Execution ownership and idempotency.** SQLite uniqueness and conditional updates grant a finite execution lease for one daily-operation key. Concurrent host or manual calls wait for or report the current state; only the lease holder may make the target-side request. A crashed or expired lease can recover without permitting a second successful same-day operation.

22. **Check-in confirmation.** A claim before noon may enter `signed_provisional`; later read-only verification may mark it `signed_confirmed`. A claim after noon may be confirmed immediately when evidence is sufficient. `signed_confirmed` requires observed balance increase or an explicit upstream credit receipt. An accepted claim without such evidence remains provisional with the wording “claimed, awaiting verification”.

23. **Keep-alive behavior.** WorkBuddy CN keep-alive sends the minimum supported real conversation request, currently modeled after a 25k-input/1-output-token request, and succeeds only after receiving a real model reply. A fake heartbeat or transport-only success is invalid. Failure creates a ten-minute cooldown, does not consume the daily success, and retries only on a later host or manual invocation. Cost is taken from the current upstream receipt; the observed value `0.02` is evidence, not a constant.

24. **Doubao idempotency caveat.** Doubao Work must remain declared `idempotent: false` because a repeated same-day request returns a generic `710010702` system error rather than a definitive already-claimed state. The local Beijing-day success gate provides product-level protection: after a successful claim, no later invocation sends another Doubao claim.

25. **Retry policy.** qka does not own periodic retries. A retryable check-in failure returns its state and waits for the next host or manual call. A keep-alive retry additionally respects the ten-minute cooldown. Permanent configuration or protocol errors are surfaced as failed/final with remediation. Sleep and wake do not trigger catch-up by themselves.

26. **Structured result and evidence.** Each account-by-operation result includes target, masked account, operation, state, timestamp, message, selected source, effect summary, `credits` and `balance` when observable, and an evidence chain with `observed`, `inferred`, and `unknown` sections. Evidence endpoints are redacted. Secrets, cookies, full headers, raw responses, and full account/device identifiers never appear in results.

27. **Status semantics.** “Credited” and “claimed but awaiting verification” are distinct UI and machine states. Missing evidence must not become either “did not happen” or “credited”. A result may say only what the observed evidence supports.

28. **Manual-run parity.** The UI's run-now action calls the same application service and state machine as host `checkin_run`. It first requests a dry run showing accounts, operations, likely credit spend, conflicts, cooldowns, and source availability. Manual execution still obeys daily idempotency.

29. **Five-tab information architecture.** The primary window contains exactly Applications, Logs, Accounts, Agent Integration, and Plugins in that order. Settings is a separate gear entry. Applications owns overall health and summaries; Accounts owns person-level account and source actions; Agent Integration owns host pairing and guidance; Plugins owns adapter trust and developer mode. The accepted information architecture prototype is the visual baseline.

30. **Menu-bar behavior.** The default app is menu-bar-only with no Dock icon unless the user enables it. The status item uses a template icon. The panel follows the status item, hides on Escape or focus loss, does not steal keyboard focus, and remains associated with the correct full-screen Space. A check-in failure badge is red; opening it leads to the detailed failure view. System notifications are optional and off by default.

31. **Failure presentation.** A failed check-in exposes target application, masked account, source type, reason, attempt count, and a next action: retry now when allowed, official re-login, wait for the next host invocation, or update/disable an adapter. A missing or stale host invocation is phrased as an observation with host-side verification guidance.

32. **Declarative settings.** Preference and privacy forms are generated from a declared configuration schema. New toggles should not require separate hand-maintained maps of UI behavior. Configuration writes use an interprocess lock, atomic replacement, backup, and schema validation.

33. **Persistence and logs.** SQLite is the source of truth for state, leases, and one-event-per-row logs. Logs roll over after 30 days and support application, account, operation, and state filters. Recovery snapshots are owner-only and atomically replaced. Logs and snapshots contain no credentials.

34. **Adapter contract.** An adapter provides manifest, discovery, optional official-login description and verification, check-in, optional keep-alive, and health checks. The host application grants only declared capability hooks for credentials, official login, outbound HTTP, state, and logging. An adapter may not declare schedules, register host plans, request local timers, or access another account's namespace.

35. **Signed adapter lifecycle.** The default market uses an index with artifact hashes, compatibility, and ed25519 signatures. qka verifies the complete artifact hash and manifest before load. Updates are checked at launch, every six hours, and on manual request. A running version remains pinned until its task finishes. A failed update keeps the previous version; with no trusted rollback version, the adapter is disabled.

36. **Developer mode.** Unsigned local adapters are disabled by default. After explicit opt-in they are marked unverified, excluded from auto-update, and restricted to one user-selected account plus one existing source for one invocation. Every load requires confirmation showing package, source, target application, and account, and writes an audit event. Unsigned adapters cannot create managed sources or trigger official refresh.

37. **Distribution and installation.** Releases use a fixed official feed plus SHA-256. The harness skill presents a dry-run plan, backs up host configuration, installs the platform artifact, clears quarantine after verification, starts the service, pairs the selected host, and verifies connectivity. It then guides the user through the host's own schedule UI and records only observed invocation evidence.

38. **Host profiles.** Each host claimed as supported has a tested profile with configuration location, HTTP or stdio transport, per-host credential write, native schedule setup and verification guidance, uninstall steps, and acceptance evidence. Writing an `mcpServers`-like entry alone does not qualify. WorkBuddy's host role and WorkBuddy CN target role are separate profiles and acceptance tracks.

39. **Automatic update.** qka waits for idle, verifies the stable feed and asset hash, health-checks the new bundle, and hands over the listener so paired hosts do not observe a gap. The previous bundle remains as rollback. Failed start or health checks restore it. Updates are disabled when running in a container.

40. **Diagnostics and dry run.** `doctor_run` returns stable `check`, `verdict`, `detail`, and `fix` fields for installation, endpoint, pairing, credentials, Keychain cooldown, recent invocation, adapter trust/effects, file permissions, and port occupation. Host-internal schedule state is always `not_observable`. Installation, pairing rotation, managed-source persistence, adapter update, and self-update expose a no-change plan before mutation.

41. **Bounded output.** All CLI modes support stable JSON output. Any subprocess or tool output is accumulated with a hard bound; exceeding it is an explicit failure rather than unbounded stdout/stderr being passed to the host context.

42. **Background wake-ups.** qka may run aligned maintenance loops for update checks, adapter refresh checks, and cooldown-state housekeeping. These loops never perform a business check-in or keep-alive. There is no local business scheduler or fallback timer.

## Testing Decisions

The primary behavioral test seam is the public MCP/application-service boundary that both the MCP transport and desktop UI invoke. Tests should submit external commands, control time, adapters, official-login outcomes, credentials, and target-side responses through test doubles, then assert only user-observable states, results, evidence, persisted user state, and side-effect calls. Tests must not assert private function calls, adapter internals, SQL layout, or implementation-specific control flow.

A good test is deterministic, scenario-oriented, and written in domain language. It should answer questions such as “does a second invocation avoid another claim?”, “does disabled mean zero credential reads?”, or “can a host tell that confirmation evidence is insufficient?” rather than “was method X called?” Controlled doubles should expose call counts and destinations where the side-effect boundary itself is the behavior under test.

1. Verify the visible tool list is constant, contains the eight agreed tools, and contains no schedule read/write/fallback capability.
2. Verify HTTP and stdio bridge calls produce equivalent external results for listing agents, account actions, dry run, status, logs, doctor, and execution.
3. Verify an unpaired client, a wrong Host/Origin, and a LAN-bound request are rejected while a correctly paired loopback client succeeds.
4. Verify first-install port selection across `43189-43299`, persistence of the selected port, and explicit refusal to silently move an already paired endpoint.
5. Verify each host can be paired and revoked independently without affecting another host.
6. Verify account discovery returns all enabled-application accounts with masked identity and source metadata, without credentials.
7. Verify manual addition opens only the declared official-login experience and exposes no password, verification-code, or QR payload input in UI, MCP schemas, or state.
8. Drive official login through `cancelled`, `pending`, `expired`, `rejected`, and `verified` outcomes; only `verified` creates a managed source.
9. Verify an official-login redirect or window close without read-only identity verification does not create an account or source.
10. Verify an imported source is accepted for execution but refuses refresh and never writes back to the target application.
11. Verify a managed source can refresh only through the declared official mechanism and becomes reauthentication-required when that mechanism fails.
12. Verify source selection with no pin, an explicit pin, healthy managed and imported alternatives, and unhealthy alternatives; assert deterministic selection and reporting of the used source.
13. Verify multiple accounts under one target application execute independently and one failure does not abort or alter the others.
14. Verify disabling an application causes zero adapter dispatch, zero credential reads, zero outbound network calls, and preservation of managed credential records; re-enabling restores them.
15. Verify deleting qka account/source records leaves a fake target application's own account data intact.
16. Verify V1 agent descriptors expose target-specific capabilities without adding target-specific tool names, including WorkBuddy CN keep-alive and check-in-only behavior for the other three applications.
17. Verify missing effect metadata is projected conservatively and appears in doctor output; complete metadata is exposed to the host.
18. Verify `plan_validate` reports accounts, actions, estimated spend, conflicts, cooldowns, and unavailable sources while performing zero network requests and zero writes.
19. Verify check-in state transitions for `pending`, `running`, `signed_provisional`, `signed_confirmed`, `already`, `none`, retryable failure, and final failure.
20. Verify Beijing-day keying with a machine clock in another timezone and boundary cases immediately before and after midnight Asia/Shanghai.
21. Verify simultaneous host and manual invocations for the same daily-operation key issue at most one target-side claim and return coherent states to both callers.
22. Verify an expired or crashed execution lease is recoverable and still cannot produce a second same-day success.
23. Verify a successful check-in suppresses later same-day claims for that account while preserving keep-alive as a separate operation.
24. Verify `none` and retryable failure do not become terminal and remain eligible for a later host invocation.
25. Verify qka performs no business execution merely because time passes, the machine wakes, or a cooldown expires.
26. Verify a successful WorkBuddy CN keep-alive requires a real model reply, consumes at most once per Beijing day, and enters cooldown after a retryable failure without consuming the success.
27. Verify WorkBuddy CN check-in and keep-alive can both run in one invocation and neither masks the other's result.
28. Verify keep-alive cost shown to the user comes from a fake current upstream receipt and is not hard-coded to the historical observed `0.02`.
29. Verify Doubao Work declares non-idempotency, a same-day generic upstream error cannot trigger another claim after local success, and the user-visible result does not claim upstream idempotency.
30. Verify credited, provisional, no-activity, retryable-failed, reauthentication-required, and final-failed states remain distinct in MCP, UI, and logs.
31. Verify an accepted claim with no observable balance or explicit credit receipt is reported as awaiting verification, not confirmed.
32. Verify evidence sections contain observed facts, labeled inferences, and explicit unknowns, with endpoint redaction and no secrets or full identifiers.
33. Verify the menu-bar red badge appears only for qualifying check-in failures, opens a complete failure detail, and optional notifications remain off by default.
34. Verify the five primary tabs and separate Settings entry, including the canonical order and ownership of account versus application actions.
35. Verify the accepted prototype states for automatic discovery, manual official login, imported-source fallback, multi-account rows, failure detail, Agent Integration, Plugins, light/dark themes, 1440-by-900 desktop, and a narrow menu-bar panel without horizontal overflow.
36. Verify the status panel does not steal input focus, closes on Escape or focus loss, and uses the template icon in both light and dark appearance.
37. Verify `status` and resources provide last invocation as an observation and never claim knowledge of a host's future schedule.
38. Verify `doctor_run` reports host-internal scheduling as `not_observable` and provides host-side guidance rather than a fabricated success.
39. Verify `log_tail` is cursor-based, bounded, filterable, and returns no secrets; exceeding the requested or allowed bound yields an explicit error.
40. Verify `feed_list` returns a stable empty result with an “unimplemented” status and does not call a target application or feed producer.
41. Verify an unsigned adapter remains disabled until explicit developer mode, is marked unverified, receives only one selected account and source for one invocation, writes an audit event, and cannot create or refresh managed sources.
42. Verify signed adapter upgrade is pinned during an active operation, activates only after validation, and falls back to the previous version on load or health failure.
43. Verify `adapter validate` rejects missing manifests, undeclared actions/effects, bad compatibility, missing entry points, and invalid package hashes without network or credential access.
44. Verify an uninstall or failed host-configuration write restores the prior host configuration and leaves another host's pairing intact.
45. Verify pairing-credential rotation invalidates only the targeted host and requires an explicit preview/apply/verification path.
46. Verify self-update waits while a fake target operation runs, swaps only after artifact verification and health check, preserves MCP call continuity, and rolls back on startup failure.
47. Verify no code advertised as a background maintenance loop mutates target-application check-in, keep-alive, or daily-operation state.
48. Verify all public CLI modes produce schema-stable JSON and that oversized subprocess output produces a bounded, explicit failure.

The repository is design-and-prototype-first and has no accepted implementation test suite yet, so there is no existing behavioral-test prior art to inherit. The accepted information-architecture prototype is prior art for user-visible UI states and layout. The live target-application probes are prior art for deriving sanitized fixtures and expected outcomes, but automated tests must use controlled doubles rather than real cookies, tokens, account IDs, device IDs, or network side effects.

Packaging, Gatekeeper, Keychain entitlement, and self-update handoff are release-pipeline acceptance checks rather than additional behavioral seams. They should run on a disposable macOS test profile and must not use a user's real credentials.

## Out of Scope

- Windows and Linux product delivery. Non-GUI cross-compilation paths may remain, but platform behavior is not promised.
- V2 target applications: Trae, Trae CN, and Qwen Office.
- WorkBuddy International and Qoder International products beyond the explicitly included Qoder V1 app.
- Keep-alive for any target application other than WorkBuddy CN.
- qka-owned account/password login, SMS-code handling, QR-content handling, token entry forms, or any equivalent login-secret collection.
- qka-owned business schedules, schedule read/write tools, schedule fallback timers, or claiming to know a host's future plan.
- Activity or discount intelligence production and consumption; only the stable empty `feed_list` placeholder is included.
- LAN sharing, remote MCP control, remote pairing, and API-key/IP allowlist products.
- Dynamic per-target MCP tool names such as a dedicated WorkBuddy or Qoder tool.
- An operating-system security sandbox that protects against malicious code already running as the same macOS user.
- Apple code signing, notarization, or a promise of Apple identity validation.
- Ensuring target-application terms compliance, immunity from anti-automation controls, or guaranteed ongoing campaign availability.
- A general-purpose automation framework, browser scraper, or scheduler unrelated to the four V1 target applications.

## Further Notes

The requirements baseline is v1.4 and consists of 21 functional requirements and 8 non-functional requirements. The accepted design suite and terminology note define this spec's domain language; implementation should use “host”, “target application”, “target account”, “login-state source”, “official sign-in”, “daily operation”, and “source preference” consistently.

Delivery is staged as milestone M1 (engine plus WorkBuddy CN and Qoder CN), M2 (full V1 user journey, all four target applications, installer, host profiles, account/source UI, and plugin development), and M3 (signed market, self-update, release matrix, and feed placeholder). The product may not claim V1 complete until all four target applications pass live acceptance, WorkBuddy CN keep-alive passes, host-native hourly scheduling has been verified on the claimed hosts, and the specified user journeys work without a host conversation.

Live probes established two fixtures worth preserving in tests and documentation: Doubao Work personal-account sign-in added `200 POINT`; a same-day repeated call did not add another benefit but returned business code `710010702 / system error`, so it must remain non-idempotent at the API declaration level and be protected by the local daily gate. WorkBuddy CN keep-alive's latest observed cost was `0.02`, but future UI and results must use the current receipt rather than that historical number as a constant.

Target-application protocols and campaigns can change. Adapter versioning, signatures, effect declarations, rollback, and evidence-based results are the intended containment strategy. A protocol change must produce an explicit unavailable, retryable, reauthentication, or adapter-update condition rather than silently weakening the security or idempotency model.

The spec follows the accepted ADR that imports are always read-only and only managed sources may be refreshed through an official mechanism. It also follows the user-selected simple-product direction: ordinary users interact through natural language in their host and through five understandable UI tabs; they should never need to know MCP tool names, adapter manifests, database state, or credential formats.
